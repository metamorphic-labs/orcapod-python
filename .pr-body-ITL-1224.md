## Iterate a stream directly (ITL-1224, first commit)

A stream is iterable: `StreamBase.__iter__` returns `iter_data()`. The documentation now writes its loops as `for tag, data in stream:`, starting with the first page (`docs/index.md`). Documentation only; no library change.

## The rule

A `for` clause (a loop or a comprehension) iterates the stream itself. `iter_data()` is written only where the method is the subject of the sentence (the streams page's `iter_data()` section, lists of read methods) or where the iterator is passed to a function as a value: `list(stream.iter_data())`, `sorted(stream.iter_data(), key=...)`, `islice(stream.iter_data(), 3)`, `next(iter(stream.iter_data()))`.

Applied to every user-facing page: `docs/index.md`, `docs/getting-started.md`, `docs/concepts/` (arrays, data-tags, file-types, function-pods, operators, sources, streams), `docs/tutorial/` (01, 04, 07). `README.md`, `docs/troubleshooting.md` and `docs/reference/` had no loop to change (`docs/reference/hashing.md` keeps `next(iter(source.iter_data()))`, a value). No docstring example in `src/` shows such a loop.

`docs/getting-started.md`, the streams concept page and the first tutorial page each say once that iterating a stream is the same as calling `iter_data()`.

## Every stream kind shown is iterable

Sources, operator results, function pod streams (`FunctionPodStream` has its own `__iter__`), function and operator nodes and job nodes, and `DerivedSource` all iterate through `StreamBase.__iter__`. Two classes have `iter_data()` but no `__iter__`: `SourceNode` and `SourceJobNode` (a job's source slots, `job.nodes["<slot>"]`). No documentation sample loops over one, so nothing here depends on it; ITL-1225 covers it. `StreamView` (what `run()` returns) has neither and is not looped over in the docs.
