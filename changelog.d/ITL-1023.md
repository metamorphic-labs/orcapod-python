### Breaking changes and migration

- A source's declared tag columns are now referential by default (ITL-1023, specification
  "Orcapod v0.4 — Referential Tags"): each is also a data column of the same name, stored
  once, so a function can read it and joins and groups use it as a tag. A script run
  unchanged gets new schemas and hashes for such sources. Pass `tag_only_columns=[...]` (or
  `tag_only_columns=True`) to keep tags plain, exactly as before; every existing golden hash
  is unchanged under that option.

### Added

- `tag_only_columns` on `DictSource`, `ArrowTableSource`, `CSVSource`, `DataFrameSource`,
  `DeltaTableSource`, the database sources and `SpiralDBTableSource`.
- `Join` merges the data columns of a referential tag both inputs join on into one column;
  plain with referential gives a referential tag. `GroupBy` keeps a referential key scalar
  in both roles. A referential non-key loses its tag role, as every non-key tag does
  (ITL-1070), but keeps its data column as a list with one element and one source-info
  token per member; the members are ordered by its values.
- A source-info column has the shape of its data column. A value merged from several equal
  elements (a referential `GroupBy` key; a `Join` key referential on several inputs) has
  one merged token instead of a list of every member's token (ITL-1017): the merging
  operation's fold (`arrow_utils.fold_system_tag_values`), `group_v1:<hex>` over the
  members' tokens in member order for a `GroupBy` key, `join_v1:<hex>` over the members'
  tokens sorted for a `Join` key. No hash or stored id changes.
- `MapTags` renames a referential tag in both roles; `tag_only=True` renames the tag only.
  `MapData` is a data-only move.
- Removing the data column of a referential tag (`SelectDataColumns`, `DropDataColumns`)
  removes its data role only and leaves a plain tag (ITL-1195).
- A function output named like a tag of its input is an error when the pipeline is built.
- Calling a function pod, `pod(stream)`, lets the input's referential tags fall through:
  the output rows carry the function's outputs and the row's own referenced columns, so
  the tags stay referential (`ReferenceFallThroughPod`). The function, its result identity
  and its result store are the plain pod's. `pod.process(stream)` is unchanged: its
  output data is the function's outputs and every output tag is plain.
- Saved job and pipeline files are at format `0.3.0`; files at `0.1.0` and `0.2.0` load
  with every declared source tag plain, as they were written.

- `Batch` works on referential tags (ITL-1017; developer decision, November 16, 2026:
  "Batch always simply takes anything and puts into list"). As for plain tags, every tag
  becomes a list; a referential tag is one column, so it is the same list in both roles and
  stays referential. Its source info is one token per member, like any data column: nothing
  is merged, so no token is folded. System tags fold as before. Plain tags are unchanged.

- A stored table states which of its tags are referential (ITL-1019): a function node's
  pipeline table marks each referential tag column with Arrow field metadata
  (`orcapod:tag_kind` = `referential`, `referential_tags.REFERENTIAL_TAG_METADATA_KEY`); a
  plain tag carries no marker. The result table never records referential status. The
  marker moves no hash and no stored path, and needs no new table layout.
- A function node reads its bindings back from its pipeline table and refuses
  (`InputValidationError`, naming the table and both lists) a table whose marker disagrees
  with what the node declares: its pod's fall-through tags, or a loaded job's saved record.
- A job or pipeline holding referential tags and fall-through pods can be saved and
  loaded; it keeps its hashes and bindings. `ReferenceFallThroughPod.to_config` and
  `from_config` work.
- An operator node stores a referential stream (`LOG`) and replays it (`REPLAY`): its
  table marks the referential tags of the operator's own output with the same marker,
  never one that came in from upstream. Every read of the table (a replay, the stored
  view `get_all_records()`, a loaded job's read) checks the marker against the node (its
  operator's prediction, or a loaded job's saved output schema) and refuses a
  disagreement (`InputValidationError`, naming the table and both lists). Source info
  stays part of each row's record hash; the marker is put on after the hash and never
  enters it.
- `DerivedSource` over a referential stream: `node.as_source()` of a function or operator
  node presents the bindings its stored table states (checked against the node's keys),
  in the plain form and with `tags_as_data`; `DerivedSource(source, tags_as_data=...)`
  over a referential source keeps the source's own. A `tags_as_data` copy of a
  referential tag is a new plain data column. Nothing new enters the identity for the
  binding: the plain form's content hash is the origin node's, and every pipeline hash
  hashes the output schema, where a referential tag is in both halves. A saved derived
  source writes no new key: its saved schema states the binding.

- `FieldMetadataKeepingDatabaseProtocol` (`orcapod.protocols.database_protocols`): a
  database states with `keeps_field_metadata` whether it keeps Arrow field metadata.
  `InMemoryArrowDatabase`, `DeltaTableDatabase` and a `ConnectorArrowDatabase` over
  `SpiralDBConnector` state `True`. The SQLite and PostgreSQL connector databases and
  `NoOpArrowDatabase` state `False`. `ExtensionAwareDatabase` states what the database
  it wraps states, and a connector database what its connector states. A database
  without the member is treated as not keeping field metadata.

- `SelectColumns` and `DropColumns` (`select_columns`, `drop_columns`) handle referential
  tags (ITL-1022). A referential tag is one column in both roles, so naming it acts on both:
  selecting it keeps it referential, dropping it (or leaving it out of a select) removes the
  column from both roles. The roles are never split and nothing is materialized. Before,
  both operators raised "not supported with referential tags yet".

### Changed

- A node that would store a referential tag refuses every database that does not state
  `keeps_field_metadata = True`, before anything is written, so an unknown database
  never passes by default. A database that states `True` is not probed. Before, only a
  database that implements `validate_records` was checked, with a probe of null-typed
  columns.

- Saved files of format `0.3.0` state every binding: each source config that takes the
  option writes `tag_only_columns` (`True` when every tag is plain), and each function
  node writes `fall_through_references` (empty for a plain pod). The format version decides
  what a file means, never a missing key: a file at `0.1.0` or `0.2.0` holds only plain
  tags, and a `0.3.0` file without these keys, or whose keys disagree with its saved
  schemas, is refused on load.

- Errors that a referential tag causes name it and the way out; no behaviour changes.
  - A bind refused because a column is a referential tag on one side and a plain tag or a
    data column on the other (listed as a missing or unexpected column) says which side
    holds the referential tag, and how to make the two agree: `tag_only_columns` on the
    source, or a slot declared with the column in both roles (ITL-1142). The bind stays
    strict.
  - `pod.process(stream)` and `pod(stream, strict=True)` refusing a referential tag the
    function does not read name the referential tags and the two ways out: `pod(stream)`,
    or `tag_only_columns`, each only where it can work (not when no data column of the
    input is a parameter of the function, except a plain `FunctionPod`'s call).
  - "Not supported with referential tags yet" names `tag_only_columns=True`, which keeps
    every tag plain as in v0.3, beside its issue.

### Known limitations

- `MergeJoin` and `MapColumns` raise "not supported with referential tags yet"
  (operator-node storage and `DerivedSource` over a referential stream are supported,
  see ITL-1019 above).
  `PollingSource` keeps its tags plain. The identities of referential streams may still
  change.

- The SQLite and PostgreSQL databases keep no Arrow field metadata, so a function node
  that would store a referential tag there is refused (`InputValidationError`, naming the
  database and the two ways out: a database that keeps field metadata, or
  `tag_only_columns`) before anything is written. The same holds for an operator node
  attached to such a database in `LOG` or `REPLAY` mode.
- SpiralDB's `keeps_field_metadata` is verified against the pyspiral fake only (first
  write, append, merge on overlap, reread). The live service is unverified. The
  connector database refuses schema evolution, so no merge can drop the marker. The
  SpiralDB connector writes a table's Arrow metadata before its rows, so a failed
  metadata write stores no row unmarked; a write that stores no row publishes nothing;
  a failed write puts the metadata entry back as it was.
- Concurrent writers to one SpiralDB table through separate connectors are not
  coordinated: one writer's rollback of a failed write can remove the metadata entry
  another writer just published, so rows can read back without their referential tag
  marker. A node refuses such a table on read (the marker must match the node), so no
  wrong binding is ever read (ITL-1190).
- Writes of differing field metadata to one table are not refused. The in-memory
  database and the connector database combine buffered and committed rows with the
  first table's field metadata, so a batch whose marker differs from the rows already
  there takes theirs. Orcapod's own writers never do this: a table's path derives from
  its schema, where a referential tag is in both halves, so one path has one binding.
  Only an outside writer can mix them, and a lost marker is refused on read (ITL-1190).
