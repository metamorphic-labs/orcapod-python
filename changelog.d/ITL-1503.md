### Changed

- A function node in ephemeral mode asks the persistent result store before the ephemeral one when it looks a result up by input data hash, which it does after it found no pipeline record for the row: such a row, whose input the persistent store holds a result for, now gets that result (recorded as persistent, not computed) where the function ran again before. A result the node's own pipeline record points to is still served first, as before. A fresh result is still saved to the ephemeral store only, and nothing is saved to the persistent store in ephemeral mode.
- A function node's result store writes conditionally: a computation that finds a result already stored for its input, when it is about to store its own, discards its own and uses the stored one. That row is reported as a cache hit. The guarantee: on one event loop or one thread, over one database object and its views, two computations for one input data hash and data context store one result, when no conditional write for that table is made from inside a callback that runs between another conditional write's lookup and the end of its commit (a schema guard during a commit, or a custom logical-type encoder during serialization, are examples). Not covered: several threads on one database object (two jobs run in threads, or a batch commit that overlaps the lookup); a conditional write made from inside such a callback; another database handle or another process; and a function with its own `result_database` called with `skip_cache_lookup=True`, which still computes again and stores another row.

### Fixed

- Equal inputs computed at the same moment on the async path stored one result each, and a read of the node gave the last of them for every such row. One result is stored, every row delivers it, and a read gives that result for each of them.
