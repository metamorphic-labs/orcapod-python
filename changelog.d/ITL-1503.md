### Changed

- A function node in ephemeral mode asks the persistent result store before the ephemeral one when it looks a result up by input data hash, which it does after it found no pipeline record for the row: such a row, whose input the persistent store holds a result for, now gets that result (recorded as persistent, not computed) where the function ran again before. A result the node's own pipeline record points to is still served first, as before. A fresh result is still saved to the ephemeral store only, and nothing is saved to the persistent store in ephemeral mode.
- A function node's result store writes conditionally: a computation that finds a result already stored for its input data hash (in its data context), when it is about to store its own, discards its own and uses the stored one. That row is reported as a cache hit. Within one process this holds for every database, over one database object and its views, on one event loop or from several threads; a writer on another database handle or in another process is not covered. A function with its own `result_database` called with `skip_cache_lookup=True` still computes again and stores another row.

### Fixed

- Equal inputs computed at the same moment on the async path stored one result each, and a read of the node gave the last of them for every such row. One result is stored, every row delivers it, and a read gives each row what was delivered for it.
