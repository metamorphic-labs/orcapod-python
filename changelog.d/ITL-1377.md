### Changed

- `DeltaTableDatabase` commits every write to an existing table as a MERGE (it appended a
  batch of new ids before), so that a commit fails when another writer added rows after
  the table was loaded. The flush then loads the table again and retries. A commit
  re-reads the stored rows, so its cost grows with the table: commit in batches (a job
  commits every 100 rows by default) rather than per row, above all to tables holding
  large values. Measured against the append it replaces, on a local disk: a one-row
  commit to a 10k-row table took about 16 ms instead of 5 ms, to a 1 GB table about
  66 ms instead of 7 ms, and to a 5 GB table about 1.2 s instead of 8 ms; 2,000 one-row
  commits took 451 s instead of 42 s (with deltalake 1.0.2 this MERGE took 249 s: per-row
  MERGEs on a table of about 2,000 files are slower on deltalake 1.6.6, so the faster
  commits ITL-1403 reports are those it measured, not these). On a cloud store each
  commit reads every data file of the table. The stored rows, their values and types,
  and every hash, record id and stored path are unchanged; only the order of the rows
  within one commit may differ.
- `DeltaTableDatabase` refuses a top-level column whose name holds a backtick, or is
  one deltalake's MERGE reserves for its own columns (`__delta_rs_source`,
  `__delta_rs_target`, `__delta_rs_operation`, `__delta_rs_delete`,
  `__delta_rs_target_insert`, `__delta_rs_target_update`, `__delta_rs_target_delete`,
  `__delta_rs_target_copy`; `MERGE_RESERVED_COLUMNS`), with `UnstorableColumnError`
  before anything is queued, and an append to a table that already holds one: delta-rs
  cannot MERGE such a table, and every commit to an existing table is a MERGE. These
  names add to the refusals made when rows are added that ITL-1403 lists, and narrow
  its statement that a table written by either deltalake version is appended to by the
  other: a table holding such a top-level name, written by any version, takes no
  further append.

### Fixed

- Two writers (two `DeltaTableDatabase` objects, or two processes) that committed the
  same new record id to one Delta table both committed it, so the id was stored twice,
  with `skip_duplicates` true or false. Now the later writer leaves the id the earlier
  one stored: each id is stored once. Writers committing other ids all commit.
- Two writers creating the same Delta table at once could lose the earlier writer's
  rows. The later create now fails and is retried as a MERGE.
- `DeltaTableDatabase.add_records` with `skip_duplicates=False` queued a row whose id
  was already queued, and the flush stored both. It now raises `ValueError`, as the
  in-memory database does.
- A table removed and created again by another writer starts over at version 0: a
  `DeltaTableDatabase` that had read the old table could take the new one's ids for the
  old one's at the same version, and skip a row with `skip_duplicates=True` as stored
  when it was not (ITL-1413). The ids read are now tied to the Delta table's own id as well as its
  version.
