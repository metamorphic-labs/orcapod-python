### Changed

- A Python `float` given for a column declared `numpy.float32` at a source or a datagram
  (`DictSource` and `ListSource` with a `data_schema` of Python types, a `Datagram` built from
  values, its `update` and `with_columns`) now issues one `ValueConversionWarning`, once per
  process, saying that Python floats are being narrowed into `numpy.float32`, that a value it
  cannot hold exactly is stored changed, and how to avoid it (pass `numpy.float32` values, or
  declare the column `float`). The values are converted exactly as before, as Arrow converts
  them, with no check of each value: no stored value and no hash changes. Whether a narrowing
  happens is decided from the types, never from the values; `numpy.float32` values and an
  Arrow column already typed `float32` never warn (ITL-924).
- A function output declared `numpy.float32` that returns a narrower NumPy float
  (`numpy.float16(0.5)`) is now held as `numpy.float32`, as an output returned as
  `numpy.float32` already was, where it was held as a Python `float`. The stored value and
  every hash are unchanged. A Python `float` returned for a declared `numpy.float32` is
  rejected as before (ITL-924).
- The error for two dict keys with one stored value now names both keys as they were given
  and the stored key (ITL-924).

### Fixed

- Dict keys that collide after conversion to the stored key type are refused. With a
  `dict[numpy.float32, V]` column, the Python float keys `1e-50` and `2e-50` are both stored
  as `0.0`: the stored value held two entries with one key, and reading it back dropped one.
  It now raises `CanonicalOrderError`, naming the column and both keys, at a source and at a
  datagram (construction, `update`, `with_columns`). The same holds for the elements of a
  `set[numpy.float32]`, which were stored twice and read back once. A NaN key is refused as
  before (ITL-924).
  This also covers optional float32 keys and elements, Python float subclasses, and
  updates on a materialized datagram that retains its Python schema.

### Known limitations

- The narrowing warning and the collision check see a column declared `numpy.float32` in a
  Python schema only. A column whose narrow float type is known only from an Arrow schema is
  not covered: a row read from a stream reports a `float32` column as `float`, so
  `Datagram.update` on such a row, and `DictSource(data_schema=<Arrow schema>)` with a
  `float32` or `float16` field, still narrow a Python float without a warning and still store
  two dict keys that collide after narrowing. There is no Python type for an Arrow
  `float16` column (ITL-924).
