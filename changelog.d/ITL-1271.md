### Added

- The rule that no operator result and no stream depends on the order of the tags or
  columns fed into it, nor on the order of the items of an argument that names a set, nor
  on the order of a commutative operator's inputs, is stated in
  the Identity & Hashing page ("Order never counts, except where you give
  it") with the places where an order is meant to count (`record_id_columns`, `GroupBy`'s
  `member_order`, a non-commutative operator's inputs, row order where it is the point).
  One test checks it for every exported operator, source and stream kind, the function
  pod forms and a job (ITL-1271).

### Changed

- `DerivedSource(origin, tags_as_data=...)` places the tag copies after the origin's data
  columns in the order of their new names, not in the order the mapping was given
  (ITL-1271). The mapping names a set: its order changes neither the columns, their order,
  nor any hash. No hash or stored value changes.

### Fixed

- `PollingSource`'s identity holds its tag columns in name order (ITL-1271), so declaring
  `tag_columns` in another order no longer gives the same source another content hash (and
  every content hash downstream of it another value). The key columns
  (`record_id_columns`) keep their order, the explicit order of a record id. A polling
  source with two or more tags declared out of name order gets a new content hash; no
  pinned golden value moves.
