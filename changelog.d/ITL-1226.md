### Breaking changes and migration

- `GroupBy` no longer depends on how its input's columns are arranged (ITL-1226). Two
  separate effects for pipelines written with 0.3.0:
  - **Member order.** The members of a group are now ordered by the non-key tags in name
    order, then by record id and source id as before; they were ordered by the non-key
    tags in the input's tag order. Affected: a `GroupBy` whose input has two or more
    non-key tags that are not in name order (for example `tag_columns=["subject", "unit",
    "probe"]` grouped by `subject`: `unit` came before `probe`). For such a `GroupBy` the
    order of every list in a group's row changes, and so do the group's folded record id
    and source id (`group_v1:...`), the `group_v1` source-info token of a data-tag key, and
    the data hash of every grouped row. Everything downstream that reads the lists
    recomputes: a function over a grouped row gets a new input and is called again. The
    hashes of the `GroupBy` itself and its stored paths do not change. A `GroupBy` with
    one non-key tag, or whose non-key tags are already in name order, is not affected,
    unless a non-key tag holds NaN (at any list depth): its members are ordered by the NaN
    rule under Fixed, which can move them too. To keep the earlier order, name the tags:
    `member_order=["unit", "probe"]`. Stored rows of every affected `GroupBy` are not
    replaced. An operator node in `LOG` or `REPLAY` (the `GroupBy` and every
    operator node after it) keeps its table: `REPLAY` returns the rows stored before the
    upgrade, and a `LOG` run adds the new rows beside them, so `REPLAY` then returns both.
    A function node after it keeps its pipeline table, so `node.as_source()` lists the
    earlier records beside the new ones. Before running such a pipeline with this version,
    delete those stored tables, or attach a new database; `clear_cache()` clears memory
    only.
  - **The order of `by`.** The keys are kept in name order: `GroupBy(by=["b", "a"])` is
    now the same operator as `GroupBy(by=["a", "b"])`, and groups are emitted sorted by
    the keys in name order (they were emitted in the order of `by`). Affected: a `GroupBy`
    with two or more keys not in name order. Its content and pipeline hash change, and so
    do its stored operator-cache path, the order of its rows, and the hashes and stored
    pipeline-table paths of every node downstream. Values do not change: the lists, folded
    ids and data hashes are as before, and a function downstream finds its stored results
    (results are keyed by the function and the input data, neither of which changes), so
    nothing is computed again; its records are written to a new pipeline table.
    For `GroupBy`'s `by` and for `TagBy`, the order of a list or tuple no longer enters
    the identity; it did before this change.

### Added

- `GroupBy(..., member_order=...)` and `stream.group_by(..., member_order=...)` (ITL-1226):
  the tags that order the members of a group, in order; the other non-key tags follow in
  name order. Only tags of the input may be named (plain tags or data-tags, not a key); a
  member is never ordered by a data value, and a data column is refused with `tag_by` as
  the way to make it a tag. `"name"` is the default order. An ordering function is
  planned and refused for now. The option is part of the operator's identity only when
  given, so a `GroupBy` without it keeps its hash.

### Changed

- `TagBy` and `tag_by` (ITL-1226): the order of the names is no longer part of the
  operator. The identity is the sorted names, the new tags follow the stream's tags in name
  order, and the names may be given in any iterable, a set included.

### Fixed

- `GroupBy` orders a member whose ordering tag holds NaN (ITL-1226): NaN sorts after
  every number and before null, at any list depth, and two NaN tie (the record id breaks
  the tie). Before, a NaN compared with nothing and the members of its group came out in
  the input's row order, so their lists and hashes depended on it. A NaN group key is
  unchanged: each row with a NaN key is a group of its own.

### Known limitations

- A raw `ArrowTableStream`'s content hash depends on the order of its `tag_columns`
  (ITL-1227); its values and pipeline hash do not, and a source's hashes do not.
