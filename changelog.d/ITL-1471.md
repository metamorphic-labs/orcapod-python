### Breaking changes and migration

- **Stored tables move to new layouts: `pdb_v2`, `odb_v2` and `tdb_v2`.** The function
  pipeline table, the operator cache and the side-effect invocation log are written at a new
  last path component. A table a release candidate wrote at `pdb_v1`, `odb_v1` or `tdb_v1` is
  reported as a table of another layout and is not read; a node that delivers side effects (a
  `SideEffectPod` node, or a function that takes the invocation context) refuses to run beside
  one, before anything is delivered. Function results (`rdb_v1`) do not move, so a job run
  again over a store of an earlier candidate records its rows again without calling a
  function. (ITL-1471)
- **An operator cache can no longer be kept in a SQLite database.** Every row of an operator
  cache is now stored with the time it was first stored (`__recorded_at`, a UTC timestamp),
  and the SQLite connector has no column type for a timestamp. An operator node with caching
  on (`CacheMode.LOG` or `REPLAY`) refuses a `SQLiteConnector` database when it is attached,
  with `UnstorableColumnError` naming the node and the column, before anything runs. A
  function node's pipeline table was already refused there. In-memory, Delta and PostgreSQL
  databases are not affected by this. Timestamp support for the SQLite connector is
  ITL-1482. (ITL-1471)
- **Every `invocation_hash` and every side-effect log key changes once.** A side effect and a
  function that takes the invocation context are keyed by the row's entry id: the hash of its
  tags, its system tags and its input data hash, with no other column. The side-effect log's
  column `record_id_hash` is renamed `entry_id`. (ITL-1471)
- **`PostRunPayload.record_id_hash` is renamed `result_id`.** It holds the id of the result
  (a UUID), not a hash. (ITL-1471)
- **`FunctionRun.entry_id` is renamed `record_id`** (the provenance record of
  `explain()`): it holds the id of the pipeline table's row. (ITL-1471)
- **`FunctionJobNode.compute_base_entry_id` is renamed `compute_instance_id`, and
  `compute_pipeline_entry_id` is removed.** The ids are computed by `orcapod.core.row_ids`.
  (ITL-1471)
- **`DataProtocol` has a new required method, `source_info_table()`**, the one-row table of a
  row's source-info columns; `Data` and `EmptyData` implement it. `EmptyData`'s unused
  `empty_source_info` argument is replaced by `source_info`, the tokens it carries.
  (ITL-1471)

### Changed

- **A row has three nested ids: entry, instance, record.** The entry id names what arrived
  (tags, system tags, input data hash). The instance id names one arrival of it with its
  provenance (the entry id and the input's source-info tokens), stored in
  `__pipeline_instance_id`; a function node looks a row up by it. The record id names one
  stored row (the content hash of the node that records it, the instance id and the result
  id), stored in `__pipeline_record_id`; it is the table's key, so nodes that share a table
  each keep their rows. See [Hashing](docs/reference/hashing.md), section 3. (ITL-1471)
- **The function pipeline table keeps every distinct record; the recomputation index is
  gone.** The columns `__pipeline_base_entry_id` and `__pipeline_recomputation_index` are
  removed, and nothing is read before a row is written. The same instance recorded again
  with the same result is one row; a recompute writes a new row, and the row recorded last
  (`__recorded_at`) is the current one. An input that arrives with other source-info tokens,
  because its upstream result was computed again, is recorded as a new instance: the
  function is not called (its result comes from the result store) and no side effect is
  delivered again. (ITL-1471)
- **The operator cache records when a row was first stored, and its entry id.** Two columns
  are stored beside the row key and are part of no key: `__recorded_at` and
  `__pipeline_entry_id`. A row passed again keeps its first time. No read of the node shows
  either column. (ITL-1471)
- **The placeholder of an ephemeral result that is gone carries source-info tokens.** Each is
  the token the result's column would have, with `EPHEMERAL_RESULT_GONE` in place of the
  result id. A node given a placeholder still calls nothing and writes no pipeline row; its
  result comes from the result store. (ITL-1471)

### Known limitations

- **A source-info token's declared type is, in some places, inferred again from its value.
  This is a stopgap, not the proper solution.** The intended rule: the type of every
  source-info token column is fixed by the pipeline, like every other column type, and is
  not meant to be taken from values. Each source and operator determines the types of its
  output token columns from its inputs' types, by its own rule. A data-tag that falls through
  a function pod is meant to keep its source-info token with its type unchanged. (A column a
  function returns is never a pass-through, even with an input's name and value: its token
  points to the function.) Today, where a data-tag falls through a function pod and where a
  table is built from rows, a token's type is inferred again from its value. That can narrow
  a declared type: a `fixed_size_list` token of a data-tag that falls through a function pod
  becomes a `large_list`, and `[None]` in a token column a `Batch` declares with two list
  levels infers one. ITL-1491 removes the re-typing. (ITL-1471)
