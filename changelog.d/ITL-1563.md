### Breaking changes and migration

- A custom function result whose source-info token is not one string is refused
  (ITL-1563): `CachedDataFunction.record_data` given a hand-built output with a list
  token for an output raises `InputValidationError`, naming the token column, the type
  given and `large_string`, before anything is written. Give each output one string
  token, or none. A token type of your own cannot be declared. Results of ordinary
  function calls are not affected, and no stored column, path or hash changes.
- A result table that already holds a list token column is not rewritten (ITL-1563).
  Only a Delta (or other persistent) result table written before this fix by a custom
  `record_data` with a list token is concerned: its path and its column type stay, so
  every later write to it, an ordinary call included, still fails as a database write
  error, and its rows stay as they are. Remove that result table (or use a new result
  database) and store the results again; there is no migration.

### Fixed

- A function result table's source-info token column no longer takes its type from the
  first write (ITL-1563). The column of every output, `_source_<key>`, is a nullable
  `large_string`, declared once (`RESULT_TOKEN_COLUMN` in `orcapod.core.result_cache`).
  Before, a custom write with a list token fixed a list type for the table, and the
  next write of the other type (an ordinary call included) failed as a database write
  error, in either order.
- A custom function result that gives no token for an output is stored with a null
  token for it (ITL-1563), so every row of a result table has the token column of
  every output. Before, such a row had no `_source_<key>` column: the in-memory
  database refused it beside rows that have the column, and Delta accepted it. A token
  column that names no output of the result is refused before anything is written.
- The stored token field is the declared nullable `large_string` whatever the written
  row's own field says (ITL-1563): a custom result whose token field is non-nullable
  no longer fixes a non-nullable column, after which a null token could not be stored.
  The values are the row's, wrapped under the declared field, never cast.
- The token type that is checked is the one the row carries (ITL-1563): a hand-built
  output made from an Arrow table whose token column is dictionary-encoded or binary
  is refused, naming that type. With ITL-1557, the row keeps the declared token
  column type even when the token is null, so the same check refuses it.
