### Changed

- `CSVSource` and `CachedSource` give the large Arrow variants of string, binary and list types (ITL-1122). A CSV file keeps no distinction between `string` and `large_string`, so `CSVSource` gave `string` from a file only because of how PyArrow reads it; it now gives `large_string`, as `DictSource`, `DataFrameSource`, `DeltaTableSource` and the SQL and SpiralDB sources do. An Arrow `schema=` given to `CSVSource` is still applied as given. `CachedSource` gave the types its cache store happened to keep (`string` from an in-memory cache, `large_string` from a Delta cache, and `large_string` with no rows); it now gives large types from every store, with rows or without. Large and non-large variants hash identically: no content hash, pipeline hash, row hash or record id moves, and no stored table changes (a cache keeps what it stored, and a Delta table written with either variant accepts rows of the other). `ArrowTableSource` and an Arrow schema the user gives keep their types.
- Every operator's output has large Arrow types on a plain stream too, as it already had inside a job (ITL-1122). The operators that pass rows through unchanged (`SelectTagColumns`, `SelectDataColumns`, `DropTagColumns`, `DropDataColumns`, `SelectColumns`, `DropColumns`, `MapTags`, `MapData`, `PolarsFilter` with no predicate, `Join`, `SemiJoin`, and `GroupBy`'s key columns) kept a `string`, `binary` or `list` column of a user's Arrow table as it was; they now give `large_string`, `large_binary` and `large_list`, with rows and without. `Join` of an input with a `string` tag and an input with the same tag as `large_string` gave the type of whichever input came first in its canonical order; it now gives `large_string` whatever the order. No hash moves.
