### Breaking changes and migration

- A Delta table that holds two columns whose names differ only in case (`a` and `A`),
  which `DeltaTableDatabase` stored before this release, can no longer be read with
  deltalake 1.6 (`OrcapodDatabaseReadError`: Delta column names are case-insensitive).
  An append to such a table is refused when the rows are added, naming the cause, with
  nothing queued. Such a store is affected only if a table of it has two such names:
  for example a function with output keys `a` and `A`, or a source with such columns.
  Read it with Orcapod 0.3 (deltalake before 1.5.1) and write it again with distinct
  names.

### Changed

- Orcapod now requires deltalake 1.6.6 or newer (was 1.0.2). A commit to a Delta table is
  faster with it: a one-row MERGE into a 10-million-row table took about 110 ms instead
  of about 380 ms, and into a 5 GB table about 1.2 s instead of about 2.6 s. Every other
  table written by either version is read and appended to by the other, with identical
  rows, for every stored table kind. New tables keep Delta protocol 1/2, with no table
  features. deltalake 1.6 no longer logs `Skipping column ... because it's a binary field`.
- `DeltaTableDatabase` refuses two columns, or two fields of one struct, whose names
  differ only in case (`a` and `A`), before anything is queued
  (`UnstorableColumnError`, or `InputValidationError` for a column or field added beside a
  queued one, or beside a stored one when schema evolution is on: without evolution Delta
  leaves an unknown column out, as before). Delta column names are case-insensitive, and deltalake 1.5.1
  and later refuses such a table. So a function job with output keys `a` and `A` now
  stops at its first write, on the sync and the async path alike. Delta folds case as
  Rust's `to_lowercase` does: for the few code points where Python's `str.lower` differs,
  the refusal comes at the flush, once, as `UnstorableColumnError`, and the batch leaves
  the queue. The in-memory and connector databases still hold such names as two columns.
- On Delta the commit is the point of truth. When rows are added, `DeltaTableDatabase`
  refuses only what it can tell for certain: names differing only in case (above), a
  stored table deltalake cannot read because two of its names differ only in case,
  another logical type
  (another extension name, or the same name with other extension metadata) over a stored
  logical column, and a struct evolution that would put two names differing only in case
  into one struct. A refusal found against a version of the table this database had
  cached is checked again against the version stored now, so a name another writer has
  since removed does not refuse the rows. Telling more rules up front is ITL-1418.
- Four kinds of refusal by deltalake at the commit are raised by the flush once, as
  `InputValidationError` ("Delta refused the commit to table ...") naming the table,
  Delta's reason and the number of rows not written, or, for two names equal under
  Delta's case folding, as `UnstorableColumnError` naming the column. Those rows leave the queue,
  the other tables of the same flush still commit, and a second flush does nothing. A
  job fails with `OrcapodDatabaseWriteError` and that cause. The permanent refusals are
  `SchemaMismatchError`, the duplicate-name error, and a `DeltaError` whose message starts
  with one of `PERMANENT_DELTA_ERROR_PREFIXES` (`type_coercion`, `Invalid data found`,
  `Unsupported CAST`): a changed field metadata, two names equal under Delta's case
  folding, a type DataFusion cannot insert or cast, and a row Delta finds invalid (a null
  in a non-nullable column, a failed CHECK constraint; a constraint whose verdict changes
  by chance would have accepted the rows later, and Orcapod writes none). Any other
  failure keeps its rows queued as before, so nothing is dropped on a guess: a storage
  error, a constraint whose evaluation itself fails, a table unreadable for another
  reason, another writer committing first, and a table that cannot be loaded at the
  flush, even when Delta's cause names two names equal under its case folding. Until ITL-1412, a job whose result batch is dropped this way can
  keep pipeline records naming those results.
- This narrows what a Delta table takes from deltalake 1.5 on: a stored column's field
  metadata cannot change in a commit. So a column whose Arrow type is recorded cannot
  gain a struct field, or have a nested nullability change, when schema evolution is on.
  A recorded column is every list and map column, and every struct holding an unsigned
  integer, a non-microsecond time type, `float16` or a fixed-size type. A struct column
  without a record still gains fields, a field may be omitted or reordered, a new column
  may be added, and an untyped `null` column takes the stored type.
- A null in a struct field stored non-nullable, also in a struct without a record, is
  refused at the commit (with schema evolution on), and those rows are not written: the
  table stays strict to the type it was first declared with. deltalake 1.0.2 stored the
  null and made the field nullable. Moving a stored table to a corrected type (a
  migration) is not offered yet. An append that makes such a field nullable while
  holding no null in it is still stored, and the field reads as nullable afterwards.
- Tables Orcapod's own nodes write are not concerned: their column types are fixed by
  their inputs' schemas, and a changed column type changes the table's path. The one
  exception is an operator whose result type depends on its data rather than on its
  input schemas, which is a bug of that operator. Example: a custom operator emitting
  list items nullable only when a value exceeds 10, in an operator node that logs
  (`CacheMode.LOG`). Such an operator now fails at the store when its result type
  changes, instead of silently changing a table's recorded type (deltalake 1.0.2 stored
  both). ITL-1410 is to refuse it earlier, at the operator.
