### Breaking changes and migration

- `DataFrameSource` accepts data frames only (ITL-1330): a pandas `DataFrame`, a Polars
  `DataFrame`, or an object that exports an Arrow C stream or C array (a pyarrow `Table`,
  `RecordBatch` or `RecordBatchReader`, a frame of another library). A dict, a list, a tuple,
  a generator or a string of Python values, a NumPy array, a pandas or Polars `Series` and a
  Polars `LazyFrame` used to build and now raise `TypeError` when the source is built; the
  message names the type given and the remedy. Move Python values to `DictSource` (rows as
  a list of dicts) or `ListSource` (a list of values), which type them by Orcapod's rules.
  To keep Polars' own typing, build the frame yourself:
  `DataFrameSource(pl.DataFrame(data), ...)`; a `Series` takes `to_frame()`, a `LazyFrame`
  `collect()`. A source over a data frame is unchanged: same rows, types, default source id
  and hashes. A saved job is unaffected: a `DataFrameSource` keeps its data in memory and
  is never saved, so a loaded job has no data for its slot until a source is bound.

### Fixed

- A `DataFrameSource` given a dict or a list of Python values no longer types them through
  Polars, around Orcapod's rules (ITL-1330): a `pandas.Timestamp` with nanoseconds was
  stored as `timestamp[us, tz=UTC]` with the nanoseconds dropped and no error, and a naive
  `datetime` as an unzoned `timestamp[us]`, although a `DictSource` refuses both. Such an
  input is now refused (above).

### Known limitations

- A pandas `DataFrame` column of dtype `object` is still typed from its values when a
  `DataFrameSource` is built (ITL-1330): `pandas.Timestamp` values with nanoseconds in such
  a column are stored as `timestamp[us, tz=UTC]` with the nanoseconds dropped, and naive
  `datetime` values as an unzoned `timestamp[us]`. Give the column a `datetime64` dtype
  (`pd.to_datetime`), which is stored exactly as given.
