### Fixed

- **An append of another logical type is refused:** every database (in-memory, Delta Lake,
  and the connector databases, directly and through `ExtensionAwareDatabase`) refuses rows
  whose column, or a field nested in it (a struct child, a list item, a map key or item),
  has the stored or pending column's storage type but another logical type identifier:
  another extension name, the same name with other extension metadata, or a logical type
  where the stored column has none, and the reverse. It raises `InputValidationError`
  naming the column and both identifiers before anything is written, whatever
  `skip_duplicates`: an append of only rows already stored is refused too (before, Delta
  wrote nothing and raised nothing for it; the in-memory and connector databases already
  refused it when the change showed in the field annotation). Before, such rows were
  accepted in several cases (a Delta column in the annotated form, extension arrays whose
  types differ only in their metadata) and read back as the stored type. An append with
  the same identifier is decided as before, except at Delta's MERGE (a batch with an id
  already stored), which now writes the identifier bytes Arrow holds, not what the
  extension's serializer answers when asked again: with a serializer that changed or
  raises, the stored form (and, for a raising one, the verdict) differs. Identifiers are
  compared as stored bytes. A place of a stored Delta table whose identifier neither the log
  nor the column's recorded type gives (a list item or map item of extension values,
  ITL-1372) is decided as before. A zero-row append, and an encoding the database cannot
  write, keep their verdict.
  (ITL-1371)
