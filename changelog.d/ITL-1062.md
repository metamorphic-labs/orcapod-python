### Fixed

- An async run calls a function as often as a sync run when several input rows carry the same input data, and stores the same rows (ITL-1062). Before, rows with equal inputs that ran at the same time each called the function and each stored its own result row (equal values under new record ids, each referenced by its own pipeline record), and the run summary counted them as computed; with 12 rows of 4 distinct inputs an unlimited-concurrency run made 12 calls and stored 12 result rows against 4 and 4. Rows that are exact duplicates (same tag, record id and data) also wrote further pipeline records, which `as_source()` returned. Now a row whose input is being computed waits for that computation, without holding a concurrency slot, and then reuses the stored result; when the computation fails, gives no result or is cancelled, the next waiting row computes the input, as on the sync path. A function pod that takes the invocation context (`ctx_arg`) is called once per distinct input data on both paths, as the sync path already did. A `CachedFunctionPod`'s own `async_execute` likewise no longer repeats a computation that is already running. Results stored more than once by earlier async runs stay in the store; a later run reuses one of them and rewrites none.
