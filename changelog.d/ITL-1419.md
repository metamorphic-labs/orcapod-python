### Breaking changes and migration

- A commutative operator (`Join`, `Rejoin`, a commutative binary operator) or a function
  pod given one stream more than once (two operands of one identity: one object, or two
  separate streams such as two sources with one source id and schema) is refused with
  `RepeatedOperandError` (an `InputValidationError`), naming the operator that got the
  repeated operand (a pod downstream of it, and a function pod whose join got it, add
  context and never replace the name) and the stream, and pointing to `MergeJoin` (ITL-1419; decided on the developer's behalf,
  November 26, 2026). Such a pod forms its identity from its operands as a set, so
  `Join()(d)` and `Join()(d, d2)` had one identity, stored path and cache entry but
  different rows (a stream whose only data columns are data-tags, joined with itself,
  repeated every row whose key repeats; in a job, which rows were kept, or whether a later
  step compiled at all, depended on the order the steps were recorded in). The refusal is
  where that set is formed, the operator's `argument_symmetry`, so it is met wherever the
  identity is: hashing the result, recording the step in a pipeline, compiling it. Rows
  computed without forming the identity (standalone `Join()(d, d).as_table()`, or a
  function pod's rows over several inputs) are computed as before. An
  operand whose identity cannot be computed (a raw stream holding a value that cannot be
  hashed) raises what hashing it raises; the rule adds no error of its own. Inputs that
  share a data column are still refused first, when the step is built (overlapping data
  columns). To join a stream with itself, use `MergeJoin()(d, d)`, whose inputs are
  ordered.

### Fixed

- A job runs an ordered operator given one stream for both inputs, `MergeJoin()(a, a)`
  and `SemiJoin()(a, a)` (ITL-1419, stage 1 of ITL-1472). A pipeline's graph edges now
  carry their input position, `(upstream, node, position)`: the argument index for an
  ordered operator, none for a commutative one (also with one input), 0 for a function or
  side-effect pod. Both orchestrators give a node one input per edge, so the operator gets
  its two inputs, sync and async, in a job made from a `Pipeline` or a `PipelineJob`, after
  `PipelineJob.load` and through `node.run()`; before, the run raised "BinaryOperator
  requires exactly two input streams". No hash, stored path, stored column or saved file
  changes: a saved file still lists each `(upstream, node)` pair once, and the positions
  are rebuilt from an operator's saved `inputs` list.

### Known limitations

- `diagram()` draws one line for the two inputs of `MergeJoin()(a, a)`: drawing one line
  per positioned edge is left to stage 2 of ITL-1472.
- An operator a loaded file keeps read-only (its config cannot be rebuilt) has its inputs
  positioned by argument index, also when it is commutative; such a node never runs.
  Saved positions are stage 2 of ITL-1472.
