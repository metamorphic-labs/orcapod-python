### Changed

- **New stored tables use a canonical column order by default.** Orcapod writes the
  record id column first and sorts every other column by name in code-point order. This
  applies to a function node's pipeline and result tables, a side-effect log, an operator
  cache, a cached source, and an observer's status and log tables. Tables used to keep
  the order of the first write, which depended on how it was built. The canonical order is the
  order SpiralDB already uses for tables with a single record-id key. The change affects
  databases Orcapod can write.
  - Reading a database directly (`database.get_all_records(path)`, a Delta table opened with
    Polars or `deltalake`, a SQL `SELECT *`) shows the table's stored column order.
  - A table stored before this change keeps its order and takes new rows in any order; a
    store may hold both kinds side by side.
  - What Orcapod shows of stored rows no longer follows the stored order at all: a job
    node's `get_all_records()`, its stored view after a load, `as_source()`, a
    `CachedSource`, `get_all_cached_outputs()`, `StatusObserver.get_status()`,
    `LoggingObserver.get_logs()` and `ObservabilityReader` each present the columns in their
    own layout (for a node: tags, system tags, data, source info), then any other column by
    name. Two changes are visible: in a function node's `get_all_records(all_info=True)` the
    bookkeeping columns (`__…`) and the input's source-info columns now follow the outputs,
    by name; in an observer's tables the tag columns follow the observer's own columns by
    name.
  - Delta now matches a batch to queued rows by column name. It previously refused a
    batch in another column order. Delta commits to an existing table with a
    conflict-safe MERGE with retry.
  - A new table keeps its entire first-write order if any column at any depth has a
    type the append comparison cannot handle (a dictionary-encoded type, a view type,
    a list view, a union, an interval, or a run-end-encoded type), a column name repeats,
    or the record id column is absent. Matching a later append by name requires the
    comparison to confirm every field. Reordering even part of such a table could leave
    the writer's own next append unmatched. Delta normalizes view types before checking
    the schema. ITL-1529 tracks the follow-up.
  - No hash, record id, stored path or layout version changes, and nothing stored is
    rewritten. (ITL-1370)
