### Changed

- **A new stored table is written in one canonical column order** — every table Orcapod
  creates in a database (a function node's pipeline and result tables, a side-effect log,
  an operator cache, a cached source, an observer's status and log tables), now has the
  record id column first and every other column sorted by name (by
  code point: upper case, then `_`, then lower case). It used to keep the order of its first
  write, which depended on how that write happened to be built. The canonical order is the
  order SpiralDB already uses for tables with a single record-id key. The change affects
  databases Orcapod can write.
  - Reading a database directly (`database.get_all_records(path)`, a Delta table opened with
    Polars or `deltalake`, a SQL `SELECT *`) shows a new table's columns in the canonical
    order.
  - A table stored before this change keeps its order and takes new rows in any order; a
    store may hold both kinds side by side.
  - What Orcapod shows of stored rows no longer follows the stored order at all: a job
    node's `get_all_records()`, its stored view after a load, `as_source()`, a
    `CachedSource`, `get_all_cached_outputs()`, `StatusObserver.get_status()`,
    `LoggingObserver.get_logs()` and `ObservabilityReader` each present the columns in their
    own layout (for a node: tags, system tags, data, source info), then any other column by
    name. Two changes are visible: in a function node's `get_all_records(all_info=True)` the
    bookkeeping columns (`__…`) and the input's source-info columns now follow the outputs,
    by name; in an observer's tables the tag columns follow the observer's own columns by
    name.
  - Delta merges or coerces a batch to the rows still queued by column name (it matched by
    position before, so a batch in another column order was refused).
  - Delta creates tables in the canonical order and uses a conflict-safe MERGE
    with retry on every commit to an existing table, whatever its column order.
  - A table keeps its original column order when the backend preserves a type
    the append comparison does not handle, such as a dictionary. Delta normalizes
    view types before applying the column order.
  - No hash, record id, stored path or layout version changes, and nothing stored is
    rewritten. (ITL-1370)
