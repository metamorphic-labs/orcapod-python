### Added

- `PipelineJob` takes a separate database for function results, `result_database=`
  (keyword-only, on the constructor, `from_pipeline`, `bind` and `load`; read back as
  `job.result_database`). Results are stored in it as given, at `<function>/...` with no job
  name, so jobs of different names that share it share function results: a job computes
  only the inputs no job sharing it has stored. Pipeline records, operator caches,
  side-effect logs and cached sources stay under each job's own database and name, so each
  job still reads only its own rows. A function that takes the invocation context
  (`ctx_arg`) shares its record of performed actions the same way. A saved job records the
  result database (`bindings.result_database`, `null` when none was given) and loading
  rebuilds it as it rebuilds the job's database; `PipelineJob.load(path,
  result_database=...)` overrides it. When the file names one that cannot be rebuilt and
  none is given, the loaded job's function nodes get no database, with a warning, rather
  than the job's own `_result` location.

### Fixed

- Several pipelines could not share function results (ITL-1408): an earlier `Pipeline`
  took a `result_database`, but when the database moved to `PipelineJob` the argument was
  dropped and every job stored its results under `<job name>/_result`. With no
  `result_database` every stored path is as before.
- A job with a separate result database commits its results before its pipeline records,
  in each batch (`commit_every_rows`) and at the end of a run, and checks
  `commit_every_rows` against the result database's `batch_size` too.
