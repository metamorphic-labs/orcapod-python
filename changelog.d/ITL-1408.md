### Added

- `PipelineJob` takes a separate database for function results, `result_database=`
  (keyword-only, on the constructor, `from_pipeline`, `bind` and `load`; read back as
  `job.result_database`). Results are stored in it as given, at `<function>/...` with no job
  name, so jobs of different names that share it share function results: a job computes
  only the inputs no job sharing it has stored. Pipeline records, operator caches and
  side-effect logs stay under each job's own database and name, so each job still reads
  only its own rows; a `CachedSource` keeps its cache in its own cache database and path,
  whatever job reads it. A function that takes the invocation context (`ctx_arg`) shares
  its record of performed actions the same way. `job.bind(result_database=None)` puts the
  results back in the job's own database. A saved job records the result database
  (`bindings.result_database`, `null` when none was given) and loading rebuilds it as it
  rebuilds the job's database; `PipelineJob.load(path, result_database=...)` overrides
  it. A saved in-memory result database is not rebuilt (a new one would be empty). When
  the file names one that is not available and none is given, the loaded job's function
  nodes get no database, with a warning, rather than the job's own `_result` location, and
  saving that job writes the binding back as it was.
- A run reads its function nodes' result tables from the store's current version when it
  starts, so results committed through another `DeltaTableDatabase` handle on the same
  directory (another job, another process) since the handle loaded the table are reused,
  and a function that takes the invocation context does not perform those actions again.

### Fixed

- Several pipelines could not share function results (ITL-1408): an earlier `Pipeline`
  took a `result_database`, but when the database moved to `PipelineJob` the argument was
  dropped and every job stored its results under `<job name>/_result`. With no
  `result_database` every stored path is as before.
- A node that takes the invocation context (`ctx_arg`) looks for completions of another
  data context in its current tables at the start of every run, not only the first: rows
  marked with another data context after its first run are refused before anything is
  delivered (`SideEffectLogDataContextError`).
- With a separate result database, a run flushes the result database before the pipeline
  database at its end and after a failure, and checks `commit_every_rows` against the
  result database's `batch_size` too.

### Known limitations

- The order of commits is not yet guaranteed across nodes or after a failed result commit
  (ITL-1412): a node's batch commit flushes the whole pipeline database, which can publish
  another node's pipeline records while that node's results are still pending in a
  separate result database, and a result commit that fails can leave the node's pipeline
  records published without their results.
