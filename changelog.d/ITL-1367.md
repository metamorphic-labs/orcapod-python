### Fixed

- **An append matches columns by name in every database** — appending rows whose columns
  are the table's columns in another order was refused by the in-memory database, by Delta
  and SQLite while the earlier rows were still pending, and by the SpiralDB test fake, so a
  job node that produced the same columns in another order than an earlier write could not
  store them. Every database (in-memory, Delta, SQLite, PostgreSQL, SpiralDB) now puts such
  rows in the order the table already has (the rows still pending, else the stored table)
  before they are queued, after a flush and within one pending batch alike, and matches
  rows still queued to the stored table by name again when they are read with it or
  written; names are matched exactly (`a` and `A` are two columns) and values are never
  matched by position. A reordered append to a Delta table is committed as an
  insert-if-missing (MERGE), as before, so two writers appending one record id still
  cannot both store it. A table keeps the column order its database gave
  the first write (SpiralDB orders a table's columns its own way: the key columns, then the
  other columns by name). An append that also adds, omits or retypes a column, and a struct
  whose fields are in another order, keep each database's own rule. (ITL-1367)
