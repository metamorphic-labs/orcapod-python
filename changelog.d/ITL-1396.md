### Breaking changes and migration

- A `CachedSource` refuses a changed row under a record id its cache holds
  (`CachedSourceChangedRowError`, ITL-1396). When the wrapped source delivers a row whose
  record id is already cached with other content (any tag, data, system-tag or source-info
  value), the read or run is refused before anything is written; the error names the source
  id, the first five record ids and the count. Before, the changed row was cached beside
  the old one and both were presented. Give changed data a new `source_id`, or a new cache
  (another `cache_path` or cache database). The same row delivered again writes nothing, and
  a row under a new record id is added, as before.
- The rule is the same for a source without key columns, whose record id is the row's
  position: a reorder, or a row inserted or removed before the last one, gives a position
  another row and is refused. Rows appended at the end are added. Declare
  `record_id_columns` for data whose rows may move.
- A cached-source table (`sdb_v2`) stores a new column, `__recorded_at`
  (`timestamp[us, tz=UTC]`): when the cache wrote the row. An `sdb_v2` cache written by a
  development version without the column cannot be read; rebuild it.

### Added

- `orcapod.errors.CachedSourceChangedRowError`.
- Each row of a cached-source table records when the cache wrote it (`__recorded_at`). No
  read presents it and it is part of no record id, source-info token or hash; a row
  delivered again keeps its first time.

### Fixed

- A `CachedSource` no longer presents two rows for one record id after its source changes
  a value, and downstream nodes no longer store results for both (ITL-1396).

### Known limitations

- The refusal checks what a source delivers. A cache table that already holds two
  different rows for one record id (written by two processes at the same moment, or by
  hand) is still read as it is.
