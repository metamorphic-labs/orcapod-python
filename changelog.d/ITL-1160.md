### Breaking changes and migration

- `map_tags` / `MapTags` and `map_data` / `MapData` refuse, by default, a mapping key that is not a column of the kind they rename (ITL-1160). Before, such a key was accepted and renamed nothing, which hid mistakes such as `map_tags` of a column that had become data after `group_by`. The call now raises `InputValidationError` naming the missing names and the columns of that kind; a name that is a column of the other kind says so (`'age' is a data column: use map_data`). The check runs when the operator is called on a stream, before any row is processed, and on the async path against the first row. A raw stream's meta (`__`) column is not a data column to rename. Migration: fix the name, use the other method (or `map_columns`), or pass `strict=False` to keep the old behaviour. `strict` is not part of the operator's identity, so no hash moves; it is saved in `to_config()`.
- The `strict` and `label` arguments of `map_tags` and `map_data` are keyword-only: `stream.map_tags(name_map, False, "label")` raises `TypeError`; write `label="label"`.

### Added

- `stream.map_columns(name_map)` and the operator `MapColumns` rename tag and data columns in one step (ITL-1160). A renamed tag stays a tag and a renamed data column stays data, with its source-info column; system tags pass through. `drop_unmapped=True` drops every tag and data column not in the mapping. As with `map_tags` and `map_data`, a name that is neither a tag nor a data column is refused unless `strict=False`, a new name taken by a column that is not renamed, or given to two columns, is refused, a `__` new name is refused when the operator is built, and a result with no data column is refused. Like `SelectColumns`, it carries no data meta (`__`) column of the input. Its identity is `("MapColumns", name_map, drop_unmapped)`.
