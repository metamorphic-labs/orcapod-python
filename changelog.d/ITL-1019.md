### Added

- A stored table states which of its tags are referential (ITL-1019): a function node's
  pipeline table marks each referential tag column with Arrow field metadata
  (`orcapod:tag_kind` = `referential`, `referential_tags.REFERENTIAL_TAG_METADATA_KEY`); a
  plain tag carries no marker. The result table never records referential status. The
  marker moves no hash and no stored path, and needs no new table layout.
- A function node reads its bindings back from its pipeline table and refuses
  (`InputValidationError`, naming the table and both lists) a table whose marker disagrees
  with what the node declares: its pod's fall-through tags, or a loaded job's saved record.
- A job or pipeline holding referential tags and fall-through pods can be saved and
  loaded; it keeps its hashes and bindings. `ReferenceFallThroughPod.to_config` and
  `from_config` work.
- An operator node stores a referential stream (`LOG`) and replays it (`REPLAY`): its
  table marks the referential tags of the operator's own output with the same marker,
  never one that came in from upstream. Every read of the table (a replay, the stored
  view `get_all_records()`, a loaded job's read) checks the marker against the node (its
  operator's prediction, or a loaded job's saved output schema) and refuses a
  disagreement (`InputValidationError`, naming the table and both lists). Source info
  stays part of each row's record hash; the marker is put on after the hash and never
  enters it.
- `DerivedSource` over a referential stream: `node.as_source()` of a function or operator
  node presents the bindings its stored table states (checked against the node's keys),
  in the plain form and with `tags_as_data`; `DerivedSource(source, tags_as_data=...)`
  over a referential source keeps the source's own. A `tags_as_data` copy of a
  referential tag is a new plain data column. Nothing new enters the identity for the
  binding: the plain form's content hash is the origin node's, and every pipeline hash
  hashes the output schema, where a referential tag is in both halves. A saved derived
  source writes no new key: its saved schema states the binding.

- `FieldMetadataKeepingDatabaseProtocol` (`orcapod.protocols.database_protocols`): a
  database states with `keeps_field_metadata` whether it keeps Arrow field metadata.
  `InMemoryArrowDatabase`, `DeltaTableDatabase` and a `ConnectorArrowDatabase` over
  `SpiralDBConnector` state `True`. The SQLite and PostgreSQL connector databases and
  `NoOpArrowDatabase` state `False`. `ExtensionAwareDatabase` states what the database
  it wraps states, and a connector database what its connector states. A database
  without the member is treated as not keeping field metadata.

### Changed

- A node that would store a referential tag refuses every database that does not state
  `keeps_field_metadata = True`, before anything is written, so an unknown database
  never passes by default. A database that states `True` is not probed. Before, only a
  database that implements `validate_records` was checked, with a probe of null-typed
  columns.

- Saved files of format `0.3.0` state every binding: each source config that takes the
  option writes `tag_only_columns` (`True` when every tag is plain), and each function
  node writes `fall_through_references` (empty for a plain pod). The format version decides
  what a file means, never a missing key: a file at `0.1.0` or `0.2.0` holds only plain
  tags, and a `0.3.0` file without these keys, or whose keys disagree with its saved
  schemas, is refused on load.

### Known limitations

- The SQLite and PostgreSQL databases keep no Arrow field metadata, so a function node
  that would store a referential tag there is refused (`InputValidationError`, naming the
  database and the two ways out: a database that keeps field metadata, or
  `tag_only_columns`) before anything is written. The same holds for an operator node
  attached to such a database in `LOG` or `REPLAY` mode.
- SpiralDB's `keeps_field_metadata` is verified against the pyspiral fake only (first
  write, append, merge on overlap, reread). The live service is unverified. The
  connector database refuses schema evolution, so no merge can drop the marker. The
  SpiralDB connector writes a table's Arrow metadata before its rows, so a failed
  metadata write stores no row unmarked; a write that stores no row publishes nothing.
