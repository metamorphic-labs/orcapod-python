### Changed

- A `SpiralDBTableSource` read whose table holds no source-info column and no content hash
  (`as_table()`, `run()`, `as_polars_df()` with the default columns) no longer builds the
  source-info tokens of every row and column only to drop them. The rows and the table are
  the same; on a table of 2.2 million rows and 13 columns the read's peak memory falls from
  10.8 GiB to 2.0 GiB (ITL-1464).
- An async job run keeps the rows a node passes on as Arrow tables of at most 8,192 rows,
  not as one pair of objects per row: in an operator job node's output, in the input of an
  operator that reads all of its input first (`PolarsFilter`, `GroupBy`, `MergeJoin`,
  `Rejoin`, `Batch` without a size), and no longer at all in the orchestrator for a job
  (which never read them). Results are unchanged. An async job of `drop_nulls`, `group_by`,
  `map_data` and a function pod over 200,000 rows peaks at 4.8 GiB instead of 19.7 GiB
  (ITL-1464).
- An operator job node keeps a large output of its run (more than 64 MiB) in a private
  temporary file, read back memory-mapped, instead of in process memory. Every read of the
  node gives the same rows; a table read from it stays valid after the node and the job are
  gone. An async job of one row-by-row operator over 1 million rows holds 0.9 GiB of its own
  memory instead of 4.4 GiB (ITL-1464).
- Reading a source and applying an operator that selects, renames, filters or tags rows
  no longer builds the source-info text of every row and column. The text is built when
  it is shown, stored or handed to a function, a part of the rows at a time, so these
  steps take a few times the memory of their data instead of tens of times (ITL-1464).
  Values, hashes and stored tables are unchanged.
- `run()` of a `SpiralDBTableSource`, and of column selections, renames, `add_tags`,
  `drop_nulls` and `filter` over one, reads the table in batches and no longer holds a result
  of more than 50,000 rows (ITL-1464). The view then has the row count and the first and the
  last 1,000 rows; it is displayed as before, and its `table`, `as_table()`,
  `as_polars_df()`, `sort_by_tags()` and a longer `head` or `tail` raise `BoundedViewError`,
  which names the stream's own methods. `stream.as_table()` and iteration are unchanged; after
  such a run `as_table()` reads the source again. Smaller results, and every other stream,
  are as before.
