### Breaking changes and migration

#### Binding refuses a source whose column types differ from the slot's (ITL-1112)

`PipelineJob.bind(sources=...)` checked a source against its slot by column names only, and
assigning `job.nodes[name].bound_source` checked nothing. A source with other column types was
accepted: every pipeline hash, built from the slot's declared schema, stayed the same, so a run
wrote rows of the new types to the stored paths of the declared ones. Both ways of binding now
compare the source's tag and data columns with the slot's: names, role (tag or data) and Python
type, the inputs of the pipeline hash. Any difference raises `SourceSpecMismatchError` naming
the slot, the column and both types, before anything is bound; a refused `bind` leaves the job
as it was, its database included. A bind that is accepted never changes a pipeline hash.

```python
slot = SourceNode(name="src", tag_schema={"id": int}, data_schema={"x": int})
job.bind(sources={"src": DictSource([{"id": 0, "x": "a"}], tag_columns=["id"])})
# v0.2.0: accepted; rows with x: str were stored under the path of x: int
# now:    SourceSpecMismatchError: ... data column 'x' is declared int but the source has str
```

`SourceSpecMismatchError` is now an `InputValidationError` as well as a `ValueError`.
Migration: bind a source whose columns have the slot's types, converting them before the bind,
or record the pipeline with a slot of the source's types (which gives it its own stored paths).
Two Arrow types that are one Python type (`int32` and `int64`) are still not told apart
(ITL-949).
