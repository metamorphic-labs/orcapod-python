### Changed

- **The type of a source-info token column is determined by the pipeline, never by the
  tokens' values.** A source builds plain `large_string` tokens, and each operator determines
  its output's token types from its inputs' types, as it does for every other column.
  Every route now keeps that type: the table built from rows between two nodes, a node's
  output, record batches, and a row shown as a table
  (`data.as_table(columns={"source": True})`). Before, a token was typed again from its
  value in several places. For the tokens that sources and operators build, nothing changes:
  no hash, stored path or stored column type moves. A hand-built raw stream keeps the token
  type it declares: a fixed-size list stays a fixed-size list (it used to become a
  `large_list`), and a list token keeps its item field's name and nullability, also in an
  operator cache. A token is typed from its value only where it is first created from a
  Python value and no Arrow type exists (`Data(..., source_info=...)`,
  `with_source_info`). (ITL-1491)
- **A data-tag that falls through a function pod keeps its source-info token with its type
  unchanged.** The token used to be typed again from its value. A column a function returns
  is not affected: its token points to the function. (ITL-1491)

### Fixed

- **Rows with a nested source-info token column behave the same on the sync and the async
  path.** A row whose token column is nested (a list of tokens, or a list of such lists)
  and whose tokens could not be typed again from their values (a null or an empty list
  inside a list, as `Batch` gives over a token column that holds nulls) raised an Arrow type error where the sync
  path builds a table from rows between two nodes, while the async path recorded the rows.
  Both paths now pass such rows on and store them, with the same token types and the same
  entry, instance and record ids. (ITL-1491)
