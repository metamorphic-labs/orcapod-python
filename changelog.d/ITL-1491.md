### Breaking changes and migration

- **A stream whose source-info token does not have the shape of its data is refused.** A
  token column's type is some list layers on top of a string, and those layers must be the
  outer list layers of its data column: a `large_list` of tokens needs a `large_list` of
  values, a fixed-size list a fixed-size list of the same size. Under its layers a token is
  a string. The values may be deeper than their tokens, and a plain string token fits any
  value. A token's list is never null at any level: a null is allowed only at the innermost
  level, where the element is a string (`["a", null]` is valid, `[null, ["a"]]` under a
  two-level token type is not); a plain string token may be null. The rule is checked where a stream is built from a table;
  a stream that breaks it raises `InputValidationError` naming the token column, its data column and both
  types. Sources, operators and functions always build tokens of the right shape, so only a
  table built by hand with `_source_*` columns is affected. Such a table used to be accepted
  because nothing checked it; downstream, a `Join` over a data-tag with a null list token
  silently stored the characters of an internal marker as the merged token, and so did a
  `Join` or `MergeJoin` over a list-of-lists token with a null inner list. (ITL-1491)
- **Inputs that declare one token column with two types are refused.** `MergeJoin` (a
  colliding data column, or a data-tag both inputs hold) and `Join` (a data-tag both inputs
  hold, whose tokens the join merges) raise `InputValidationError` naming the column and
  both types, on the sync and the async path, whether or not a key matches. A `Join` over
  such a data-tag used to fail with `ValueError: cannot merge the source info of a list
  with that of a scalar` when a key matched and to complete when none did; `MergeJoin`
  already refused a colliding column. See the known limitation below for the case that
  ordinary sources reach. (ITL-1491)

### Changed

- **The type of a source-info token column is determined by the pipeline, never by the
  tokens' values.** A source builds plain `large_string` tokens, and each operator determines
  its output's token types from its inputs' types, as it does for every other column. A row
  read from a stream keeps that type where it used to be typed again from its value: in the
  table built from rows between two nodes, in a node's output, in a row shown as a table
  (`data.as_table(columns={"source": True})`, and the Python type
  `data.schema(columns={"source": True})` reports), in the rows an async `Join` merges, in
  the element `Index` takes from a list of tokens, in a function pod's stream outside a job,
  and in record batches. For the tokens that sources and operators build, nothing changes:
  no hash, stored path or stored column type moves. A token is still typed from its value
  where it is first created from a Python value and no Arrow type exists
  (`Data(..., source_info=...)`, `with_source_info`). (ITL-1491)
- **A hand-built raw stream keeps the token type it declares.** A fixed-size list of tokens
  (over a fixed-size list of values) stays a fixed-size list, where it used to become a
  `large_list`, and a list of tokens keeps its item field's name, nullability and metadata,
  also in an operator cache. (ITL-1491)
- **A data-tag that falls through a function pod keeps its source-info token with its type
  unchanged.** The token used to be typed again from its value. A column a function returns
  is not affected: its token points to the function. (ITL-1491)

### Fixed

- **Rows with a nested source-info token column behave the same on the sync and the async
  path.** A row whose token column is nested (a list of tokens, or a list of such lists)
  and whose tokens could not be typed again from their values (an empty list, or a null
  inside a list of lists) raised an Arrow type error where the sync path builds a table from
  rows between two nodes, while the async path recorded the rows. Both paths now pass such
  rows on and store them, with the same token types and the same entry, instance and record
  ids. (ITL-1491)
- **An async `Join` writes the token of a merged data-tag with the type its inputs
  declare.** It rebuilt the merged token from its Python value, so a list token that the
  sync path kept as declared became another list type on the async path, and a job run on
  one path could not be continued on the other over the same store. (ITL-1491)
- **`Index` gives the element's token the type of the token list's items.** It typed the
  token again from its value, so a list item's type could change (a fixed-size list became a
  `large_list`). An element that is a null where the remaining token type is a list is
  refused with `InputValidationError` naming the column, on both paths. (ITL-1491)
- **A function pod's stream outside a job shows list-valued source-info tokens.**
  `pod(stream).as_table(columns={"source": True})` raised `ValueError: Unsupported Python
  type` when a data-tag that falls through the function had a list token. (ITL-1491)
- **An async `Join` keeps a token that looks like its internal marker.** A column the join
  does not merge keeps its own token on both paths. The async path used to replace a token
  that began with the join's internal marker text by a `join_v1:` digest. (ITL-1491)
- **`MergeJoin` reports the same first disagreement in every process.** When several
  columns of its two inputs disagree in type, the one first in name order is reported; which
  one was reported used to follow the interpreter's hash seed. (ITL-1491)

### Known limitations

- **A `Batch` of single values cannot be joined with a source that already holds lists of
  them, on that column.** The two have the same values and data type but different
  source-info tokens: a list of tokens (one per member) after `Batch`, one plain token per
  list in the source. A `Join` where that column is a data-tag of both inputs, or a
  `MergeJoin` where it collides, refuses the inputs with `InputValidationError` naming the
  token column and both types. Bring both inputs to one form before the join: batch both,
  or neither. Whether the two forms should join is ITL-1522. (ITL-1491)
- **A record batch sent into a record-batch channel is not checked against the token-shape
  rule.** The stream built from the channel's batches is. The channels are not used by jobs
  yet; checking a batch where it is sent is ITL-1526. (ITL-1491)
- **An input that sends no row over a bare row channel declares no token type.** A `Join`
  run directly through `async_execute` over row channels (outside a job) compares its
  inputs' token types from their first rows, so it cannot refuse an input that sends none;
  the sync call and a job on either orchestrator refuse it. Carrying the declared types over
  row channels is ITL-1527. (ITL-1491)
- **Rows an async run holds instead of running are not checked against the token-shape
  rule.** The rule is checked where a stream is built. The sync orchestrator builds a held
  node's rows into a stream, and the async orchestrator hands them on without building one,
  so a held row built by hand with an invalid token shape is refused on sync and accepted
  on async. Rows that come from a stream were checked when it was built. Making the two
  routes agree is ITL-1534. (ITL-1491)
