### Changed

- **The type of a source-info token column is determined by the pipeline, never by the
  tokens' values.** A source builds plain `large_string` tokens, and each operator determines
  its output's token types from its inputs' types, as it does for every other column. A row
  read from a stream keeps that type where it used to be typed again from its value: in the
  table built from rows between two nodes, in a node's output, in a row shown as a table
  (`data.as_table(columns={"source": True})`, and the Python type
  `data.schema(columns={"source": True})` reports), in the rows an async `Join` merges, in a
  function pod's stream outside a job, and in record batches. For the tokens that sources
  and operators build, nothing changes: no hash, stored path or stored column type moves. A
  token is still typed from its value where it is first created from a Python value and no
  Arrow type exists (`Data(..., source_info=...)`, `with_source_info`). (ITL-1491)
- **A hand-built raw stream keeps the token type it declares.** A fixed-size list stays a
  fixed-size list (it used to become a `large_list`), a list token keeps its item field's
  name, nullability and metadata, also in an operator cache, and a null token keeps its
  column's type while it passes through operators (so `Batch` over null list tokens gives a
  list of lists). The instance id and the stored pipeline row of a null token are unchanged:
  a `large_string` null. (ITL-1491)
- **A data-tag that falls through a function pod keeps its source-info token with its type
  unchanged.** The token used to be typed again from its value. A column a function returns
  is not affected: its token points to the function. (ITL-1491)
- **Inputs that declare one token column with two types are refused.** `MergeJoin` (a
  colliding data column) and `Join` (a data-tag both inputs hold, whose tokens the join
  merges) raise `InputValidationError` naming the column and both types, on the sync and the
  async path, whether or not a key matches. Only hand-built raw streams can declare such
  types (for example a fixed-size list in one input and a `large_list` in the other). Such a
  job used to complete, because both token columns were typed again from their values before
  the operator saw them, which silently changed the fixed-size list. Declare one type in
  both inputs. (ITL-1491)

### Fixed

- **Rows with a nested source-info token column behave the same on the sync and the async
  path.** A row whose token column is nested (a list of tokens, or a list of such lists)
  and whose tokens could not be typed again from their values (a null or an empty list
  inside a list, as `Batch` gives over a token column that holds nulls) raised an Arrow type
  error where the sync path builds a table from rows between two nodes, while the async path
  recorded the rows. Both paths now pass such rows on and store them, with the same token
  types and the same entry, instance and record ids. (ITL-1491)
- **An async `Join` writes the token of a merged data-tag with the type its inputs
  declare.** It rebuilt the merged token from its Python value, so a list token that the
  sync path kept as declared became a `large_list` on the async path, and a job run on one
  path could not be continued on the other over the same store. (ITL-1491)
- **A function pod's stream outside a job shows list-valued source-info tokens.**
  `pod(stream).as_table(columns={"source": True})` raised `ValueError: Unsupported Python
  type` when a data-tag that falls through the function had a list token. (ITL-1491)
