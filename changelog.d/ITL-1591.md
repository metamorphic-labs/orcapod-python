### Breaking changes and migration

- **`float32` and `float16` are refused as a dict key type and as a set element type**
  (ITL-1591). A float stored under such a type is narrowed, and two distinct floats can
  narrow to one stored value (`1e-50` and `2e-50` both become `0.0`), so a dict or a set
  lost an entry without notice. A declared type with such a key or element, at any nesting
  depth (a dict in a list, a dict as a dict value, a dict in a tuple or a user-class field,
  an Arrow `map`), now raises `NarrowFloatKeyError` (an `InputValidationError`) naming the
  column and the key or element type, where the type is declared: a source's Python or
  Arrow schema, the table given to a source or to an `ArrowTableStream`, a datagram's
  schema or table, and a function pod's parameters and outputs when the pod is defined
  (`-> dict[np.float32, int]`, `set[np.float32]`). The check reads types only, never a
  value. Declare the key or element as `float64` (`float` in Python, `pa.float64()` in
  Arrow), or use another type. `float32` and `float16` are still accepted as a plain
  column, a list element, a struct field and a dict value.

### Known limitations

- A plain value (not a dict key or set element) stored into a column that an Arrow schema
  declares `float32` or `float16` is still narrowed without a warning: `0.1` under
  `pa.float16()` is stored as `0.0999755859375` (ITL-1613).
- A struct column whose fields are exactly `key` and `value` has the stored shape of a dict
  once `Batch`, `GroupBy` or `MergeJoin` collects it into a list. With a `float32` or
  `float16` field `key`, that result is refused as a dict keyed by a narrow float.
