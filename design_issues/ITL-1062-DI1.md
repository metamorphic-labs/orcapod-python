## `src/orcapod/core/nodes/function_node.py`

### DI1 — An async run called a function again for an input already being computed, and stored more rows than sync
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1062

When several input rows of a function job node carry the same input data, the sync path calls
the function once per distinct input: the first row stores its result, and a later row with the
same input data hash finds it in the result store (`ResultCache.lookup`); an exact duplicate
(same tag, record id and data) is served from the node's own results of the run, reported
`cached=True`, and writes no pipeline record. The async path started one task per row and each
task looked the result up before any of them had stored it, so rows with equal inputs that ran
at the same time all called the function and each stored its own result row (the same values
under a new record id, each referenced by its own pipeline record, `computed=True`). Exact
duplicates also missed the node's results of the run and wrote further pipeline records at
recomputation index 1, 2, ..., so `as_source()` returned them too. With 12 rows of 4 distinct
inputs, unlimited concurrency: 12 calls and 12 result rows against 4 and 4; the run summary
counted every row as computed. Node rows and values were always right, and a later run reuses
one of the duplicate result rows (the most recent).

**Rule:** sync and async runs call a function equally often for the same inputs and store the
same result rows and pipeline records.

**Fix:** `async_execute` of a function pod keeps, per call, the inputs being computed by
in-flight key (`_in_flight_key`: the input data hash for a `CachedFunctionPod`, the key of its
result store; `None`, no sharing, for a pod without a store). A row whose input is being
computed waits for that computation without holding a concurrency slot; the computing row hands
on in a `finally`: after a result every waiting row runs and finds it stored, otherwise the
first waiting row computes the input, as the next row does on the sync path; when an error ends the
run (`fail_fast`, a store error) the waiting rows are cancelled with it. A row's function
raising, giving no result or cancelling itself therefore never leaves a waiting row behind.
`FunctionJobNode.async_execute` serves an exact duplicate from the run's results as the sync
path does (`cached=True`, the earlier row's result, no pipeline record). No hash, golden value,
stored layout or public API changes. Rows stored twice by earlier async runs stay stored and
are reused, never rewritten. Regressions: `tests/test_pipeline/test_async_duplicate_inputs.py`.
