## Cross-cutting

### LN1 — Large normalization applied unevenly across sources and operators
**Status:** in progress
**Severity:** medium
**Issue:** ITL-1122

The rule (developer, November 14, 2026): every Arrow table Orcapod creates has its string, binary
and list types in their large variants; an Arrow table or schema the user made, and a store that
keeps the large / non-large distinction recoverably, keep the types as given. Measured on `main`
3a7f3850: `CSVSource` gave `string` (a CSV file keeps no distinction); `CachedSource` gave the
types its cache store kept (`string` from an in-memory cache, `large_string` from Delta and with
no rows); on a plain stream, the operators that pass rows through (select, drop, map, a filter
with nothing to filter, `Join`, `SemiJoin`, `GroupBy`'s key) kept a source's `string` while every
operator inside a job gave `large_string`, and `Join` of a `string` and a `large_string` input on
a shared tag took the type of whichever input came first in canonical order. No shipped source
store (CSV, Delta Lake, SQLite, PostgreSQL, SpiralDB) keeps the distinction.

**Fix:** `CSVSource` (without `schema=`) and `CachedSource` normalize the table they present
(`arrow_utils.normalize_table_to_large_types(..., keep_null=True)`). Every operator's sync result goes through
`core/operators/large_types.with_large_types` (beside `without_input_meta`, in `UnaryOperator`,
`BinaryOperator` and `Join`), so an operator gives large types on a plain stream as inside a
job, and `Join` no longer takes a side.
