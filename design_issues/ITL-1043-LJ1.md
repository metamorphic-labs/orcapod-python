## `src/orcapod/pipeline/job.py` — reading a loaded `PipelineJob`

### LJ1 — a saved job loses column nullability, and does not record the run content hash of an operator node
**Status:** in progress
**Severity:** high
**Issue:** ITL-1043

Found November 12, 2026. Evidence and scripts: `superpowers/specs/itl-1043/FINDINGS.md`.

- `serialize_schema` (`src/orcapod/pipeline/serialization.py`) writes each column as the Arrow
  type of its Python type. An Arrow `DataType` has no field nullability, so `int | None` and
  `int` are both saved as `"int64"` (nested nullability survives in the type text; only the
  top level is lost). A loaded job's source nodes therefore have non-null schemas, a
  different pipeline hash from the run's, and every loaded node's `output_schema()` drops
  `| None`. An operator node rebuilt with its operator recomputed its pipeline hash from them
  and looked for its cache under another table path; `Pipeline.load` followed by
  `PipelineJob.from_pipeline(sources=...)` still does, so REPLAY reads no rows there and a
  LOG run writes a second table under the wrong path.
- `PipelineJob.save` records the run content hash of function nodes only
  (`run.node_job_content_hashes`). A loaded operator node over in-memory sources (not saved)
  cannot reproduce the content hash its rows are stored under, so it cannot select them.
- The operator's `cache_mode` is not saved (ITL-977).

The running node's hashes are the intended ones: nullability is part of the schema hash
(`docs/reference/hashing.md`; golden `datagram.json` `arrow_source.int64` against
`arrow_source.int64_nullable`, `schema.json` `multi_field.nullable_type`). No live hash,
stored path or golden value is wrong; only what a loaded job reconstructs.

**Partial fix (ITL-1043):** a loaded operator node takes the pipeline hash saved in its
descriptor, the run's, so it reads the table its run wrote; and in REPLAY it raises, instead
of returning zero rows, when that table holds rows none of which carries its content hash.
Saving nullability and the operator run content hash in the job file is a saved-format
decision pending with the developer.
