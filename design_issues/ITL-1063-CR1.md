## `src/orcapod/pipeline/` — completed work on unchanged reruns

### CR1 — Job reruns rebuild rows and hashes despite retained function results
**Status:** resolved
**Severity:** high
**Issue:** ITL-1063

An unchanged job visits every node again. The sync orchestrator materializes retained
`(Tag, Data)` objects as a new Arrow stream, losing their memoized hashes. Operator
execution constructs a new stream despite holding a previous output. Async function
execution reloads stored results on every run. SpiralDB sources pin a table version but
rescan it and rebuild provenance on each read.

Measured at `89160c47`, a 1,000-row flat job's warm sync run performs 2,000 Arrow hashes
and its async run 1,000, with no user-function calls. Grouping the source into 10 rows still
reruns GroupBy and performs 20 hashes on both orchestrators. A retained standalone stream
read reuses its objects and does not repeat this work.

Approved design: `superpowers/specs/2026-11-13-pipeline-cache-reuse-design.md`.
Reproduction: `uv run python bench/bench_pipeline_cached_rerun.py --rows 1000`.

Completed graph execution now retains operator results and exact-row entry IDs against
known unchanged snapshots. Sync boundaries retain Arrow-decoded row views to preserve
declared-schema behavior; async functions reuse their valid in-memory results. Pinned
Spiral sources publish retained batch streams only after complete successful reads.
Unknown sources, direct node calls, changed bindings and failed work remain conservative.

Validated with 11,625 passing tests (119 skipped, 19 expected failures), zero type-check
errors, clean Ruff checks and independent review. Warm benchmark runs perform zero new
Arrow hashes and zero GroupBy computations. Remaining traversal/materialization costs
and potential further optimizations are tracked by ITL-1064.
