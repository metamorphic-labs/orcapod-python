## `src/orcapod/core/operators/` — Async execution

### AH1 — An async run deadlocked when a consumer stopped reading one of its inputs
**Status:** in progress
**Severity:** high
**Issue:** ITL-1075

The async orchestrator joins nodes with bounded channels, so every node must keep reading
each input channel to its end: a consumer that waits on something before it reads an input
blocks that input's producer once the channel is full. Two consumers did:

- `SemiJoin.async_execute` collected its right input before it read its left one. When one
  node `A` fed both inputs (`SemiJoin(C, A)` with `C` computed from `A`, or `SemiJoin(A, C)`,
  or `SemiJoin(A, B)` with `A` and `B` from one source), the channel into the unread left
  input filled, every node between `A` and it blocked, `A` could not finish its right-side
  rows, and the run waited forever. A computing function node spawns one task per input row
  without a limit (no `max_concurrency`) and so absorbs its whole input, which hid the cycle
  on a first run; a run that found every row stored, or a graph of operators only, hung once
  the rows exceeded what the channels in the cycle hold (about 3 x `buffer_size` + 130).
- `OperatorNode.async_execute` in `CacheMode.REPLAY` served its stored rows without reading
  its inputs, so any upstream with more rows than a channel holds blocked forever.

Every other `async_execute` (the unary operators, `Join`, `MergeJoin` and the barrier
default, function, side-effect and source nodes) reads every input to its end.
