## `src/orcapod/semantic_types/universal_converter.py`

### UC4 — A decimal column has no Python type: a saved job cannot rebuild its source
**Status:** open
**Severity:** medium
**Issue:** ITL-1323

`arrow_type_to_python_type` has no mapping for an Arrow decimal (`decimal128`,
`decimal256`): it returns `Any` and logs "no mapping for Arrow type". A job's source slot
saves its declared schema from the Python types, so a decimal column is saved with the type
text `null`. `PipelineJob.load` then cannot rebuild a source with a decimal column: the
rebuilt source does not match the slot, the source is left unbound and a warning says it
could not be reconstructed. A source's own `from_config(to_config())` is not affected (a
`CSVSource` saves its explicit Arrow schema, ITL-1315). Found while fixing that reload; the
job round trip of a `CSVSource` with a `decimal128(10, 2)` column is a strict xfail in
`tests/test_core/sources/test_csv_source_schema_config.py` until this is fixed.

How a decimal is typed in Python (for example `decimal.Decimal`, with precision and scale
kept on the Arrow side) is to be decided and written down; if it moves a hash, the moved list
needs the developer's approval. Related: hashing the Arrow schema instead of the Python types
(ITL-640).
