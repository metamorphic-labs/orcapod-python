## `src/orcapod/databases/` — appending another logical type

### LI1 — An append of another logical type over the same storage type was accepted and read back as the stored type
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1371

A table holds one logical type per column and per nested field. An append that gave a
column the same storage type but another logical type identifier (another extension name,
the same name with other extension metadata, or a logical type where the stored column has
none, and the reverse) was accepted in several places, and every appended row then read back
as the stored type, a type it was never written as:

- `DeltaTableDatabase`, a top-level column in the annotated form (storage type with
  `ARROW:extension:name` / `ARROW:extension:metadata` field metadata, the form
  `ExtensionAwareDatabase` passes on and a stored column reads back in): `_column_change`
  left a logical column's extension keys out of its metadata comparison and relied on the
  type check, which compares storage types only. This is the case reported.
- Extension arrays (in-memory and Delta, at every depth): pyarrow's equality of two Python
  extension types ignores their serialized metadata, so two types with one name and other
  metadata compare equal; the ITL-1334 checks (`appended_field_change`) treat an extension
  type as a leaf and left it to that equality.
- `DeltaTableDatabase`, a committed table: the held column is the storage type with the
  annotation, while the rows given are extension arrays, and the same short cut applied.

**Fix:** one rule, `databases/utils.logical_identity_change`, over `IdentityNode`s
(`identity_node` for a field as given, `first_logical_identity_change` for schemas): at every
column and nested place (struct children by name, list items of every kind including list
views, map keys and items, union members, dictionary values, run-end encoded children, and
an extension type held directly as another's storage, one extension level at a time; a
dictionary is an encoding, so its values stand where it stands), the raw identifier bytes
must be the held ones; no logical type is an identifier too. The bytes are those Arrow holds
(an extension type's C data interface export, never its serializer called again; for an
extension type whose storage is another extension type, which Arrow cannot export, that
level is not known and not compared, its storage still is) or the `ARROW:extension:*`
annotation; never decoded to decide (a name that is not UTF-8 is shown as a bytes literal,
`b'\xff'`, a form no text name takes), never Arrow type equality. A given column's field and
each of its chunks are compared (pyarrow lets the chunks of one Python extension class carry
other serialized metadata). Places pair by name, or by
occurrence where a name repeats among siblings (Arrow allows two struct children, union
members or columns of one name), never by name alone. Only a bare `pa.null()` claims no
type; an annotated null claims its annotation.

The rule only ADDS a refusal where it KNOWS the identifiers differ: from the fields as given
(in-memory, a pending batch, a connector's stored schema) and, for a stored Delta table, from
the Delta log, which keeps the field metadata of a column and of each struct child byte for
byte (`_delta_identity_node`). Where the held identifier is not reliably known it abstains:
a Delta list item, map key or item (the log keeps no metadata there, and the recorded type
is read through the Arrow registry, which may rewrite the metadata), and, the one condition
for a missing identifier, a stored Delta place with no identifier in a column whose log
records no Arrow type (`orcapod:arrow_type`): Delta writes a dictionary of extension values as
plain values with no identifier and no record (pre-existing, ITL-1372), so there the absence
proves nothing, whatever the given encoding; with a record, the column is known to hold no
logical type and another identifier is refused, dictionary-encoded or not. Also where a side is an untyped
null (`pa.null()`, which holds no value and claims no type), it abstains, and the database's
other checks decide exactly as before. A place only one side has (struct evolution, another
kind of type) is left to those checks too. The ITL-1334 comparison is unchanged and runs after
it. In-memory and connector databases apply it in `add_records`, Delta in `add_records`
(`_identity_refusal`, pending and stored) and again at flush (`_append_refusal`).
A refusal raises `InputValidationError` naming the column, the path and both identifiers'
text, before anything is buffered, whatever `skip_duplicates`: an append whose column carries
a known different identifier is refused, duplicate-only or not (on main a duplicate-only
append with `skip_duplicates` was a silent no-op; nothing was or is written), while a
duplicate-only append of the same identifier stays a no-op. The order is the same with
either setting: in Delta the rule reads the log only and runs first, before anything decodes
a stored type (the duplicate scan, the held columns), so no read failure can come before it;
only when it passes or abstains does the duplicate scan run, and a read failure there
propagates as a read failure. The database type matrix appends each logical type again under another extension
name, which every database refuses.

So the only appends whose verdict differs from main are those with a known different
identifier. Where Delta stored a nested extension type as plain storage (a list item or map
value, ITL-1372) the rule abstains and main's verdict stands (a second map is accepted with
any identifier, a second list refused for its item's name); a column Delta wrote from a
dictionary of extension values takes the same type again, as a dictionary or not, as on
main. Also pre-existing (ITL-1372):
Delta refuses any second append of a registered logical type nested in a column with a
recorded type, even the identical one. Probe: `docs/dev/scripts/itl_1371_logical_identity_appends.py`.
