## `src/orcapod/databases/` — appending another logical type

### LI1 — An append of another logical type over the same storage type was accepted and read back as the stored type
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1371

A table holds one logical type per column and per nested field. An append that gave a
column the same storage type but another logical type identifier (another extension name,
the same name with other extension metadata, or a logical type where the stored column has
none, and the reverse) was accepted in several places, and every appended row then read back
as the stored type, a type it was never written as:

- `DeltaTableDatabase`, a top-level column in the annotated form (storage type with
  `ARROW:extension:name` / `ARROW:extension:metadata` field metadata, the form
  `ExtensionAwareDatabase` passes on and a stored column reads back in): `_column_change`
  left a logical column's extension keys out of its metadata comparison and relied on the
  type check, which compares storage types only. This is the case reported.
- Extension arrays (in-memory and Delta, at every depth): pyarrow's equality of two Python
  extension types ignores their serialized metadata, so two types with one name and other
  metadata compare equal; the ITL-1334 checks (`appended_field_change`) treat an extension
  type as a leaf and left it to that equality.
- `DeltaTableDatabase`, a committed table: the held column is the storage type with the
  annotation, while the rows given are extension arrays, and the same short cut applied.

**Fix:** one rule, `databases/utils.logical_identity_change` (with
`first_logical_identity_change` and `field_logical_identifier`), compares the logical type
identifier of every column and nested field (struct children by name, list items, map keys
and items, an extension's storage) in either form, by identifier, never by Arrow type
equality. In-memory and connector databases apply it in `add_records` before the ITL-1334
check, Delta in `_column_change`, at add time and again at flush. A refusal raises
`InputValidationError` naming the column, the path and both identifiers' text, before
anything is buffered; an append with the same identifier is accepted as before. Columns are
matched by name, so the order of the given columns plays no part. Delta's held column now
carries the extension annotations the Delta log keeps on struct children
(`_with_extension_annotations`), so a struct of an extension type can still be appended to.
As in the other Delta checks, the rule runs after `skip_duplicates` has dropped the rows
already stored: an append that writes nothing is not refused. The database type matrix
appends each logical type again under another extension name, which every database refuses.

A consequence of ITL-1372 (Delta writes a list item or a map value of an extension type as
plain storage on the first write): a second append of the same nested extension type to a
committed Delta table was accepted on main and stored as plain storage; it is now refused,
because the held column has no logical type. The first write is still accepted and still
loses the type until ITL-1372. `test_delta_nested_extension_second_append_is_refused` pins
this. Probe: `docs/dev/scripts/itl_1371_logical_identity_appends.py`.
