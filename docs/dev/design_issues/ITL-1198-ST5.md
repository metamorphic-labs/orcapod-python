## `src/orcapod/core/streams/arrow_table_stream.py` — tag order

### ST5 — `keys()` lists tags in `tag_columns` order, `output_schema()` in physical order
**Status:** open
**Severity:** low
**Issue:** ITL-1198

`ArrowTableStream.keys()` gives the tag columns in the order of its `tag_columns` argument,
while `output_schema()` gives them in the table's physical column order (`_tag_schema` is the
table schema filtered to the tags). The data keys and the data schema agree: data-tags first,
in tag order, then the other data columns in physical order (ITL-1205). A plain source shows the difference: over a table with columns `b, a, v` and
`tag_columns=["a", "b"]`, `keys()` lists `a, b` and `output_schema()` lists `b, a`.

`TagBy` (ITL-1175) meets it: it keeps the input's layout, its data order is the predicted one
(data-tags first, ITL-1205), and its predicted tag order is the requested one, which `keys()` reports.
For names given in another order than the table's, `output_schema()` of the computed stream
lists the new tags in table order. No layout can give both orders, since one physical order
decides both schemas.

No hash depends on either order (`Schema` equality and the pipeline and content hashes are
order-insensitive), and column order is not part of a stream's identity (ITL-1112). The fix
is to decide one order for both methods in `ArrowTableStream`, without moving any stored
table's layout.
