## `src/orcapod/databases/delta_lake_databases.py` — Delta statistics columns

### DS2 — delta-rs warns on every write for each binary column; lookups cannot use file statistics
**Status:** resolved
**Severity:** low
**Issue:** ITL-1187

By default delta-rs collects minimum and maximum statistics for the first 32 columns of each
file it writes and logs `WARN deltalake_core::writer::stats ... Skipping column ... because
it's a binary field` for each binary column on every write. Orcapod stores record ids and
hashes as binary, so every commit of a `DeltaTableDatabase` logged several such lines, which
workshop attendees would see on every table they create (developer decision, November 16,
2026: fix it at table creation, not only document it).

Also found (for the performance project, not changed here): no Orcapod lookup uses these
statistics. The columns lookups filter on are `__record_id`, `__input_data_hash`,
`__node_content_hash` and `__pipeline_base_entry_id`, all binary, for which delta-rs makes no
statistics; the fifth, `__data_context`, is a string but matches every row. Lookups do not
push a filter into Delta anyway: `DeltaTableDatabase` reads the table into memory and
answers from its index (ITL-919). The MERGE predicate is on `__record_id`, so MERGE cannot
prune files by statistics either. File skipping for lookups would need the looked-up
columns stored in a type delta-rs keeps statistics for, and a lookup that pushes its
filter into the Delta read.

Seen while testing (delta-rs 1.0.2, not changed here): MERGE into a table that has a column
whose name holds a backtick fails (`Expected close delimiter`), with or without the property.

**Fix:** `DeltaTableDatabase` creates every new table with `delta.dataSkippingStatsColumns`,
from one rule, `delta_statistics.statistics_configuration`: the top-level columns whose type
(or extension storage type) is an integer, `float32`/`float64`, boolean, string, `date32`,
timestamp or `decimal128`, whose name holds no comma or backtick, and whose name is not
also a nested field's name in the schema (delta-rs matches a listed name against nested
leaf names too, so `v` would also select a binary `rec.v` and warn). When none qualifies,
the table gets `delta.dataSkippingNumIndexedCols = 0`, since delta-rs refuses an empty list.
The list is an allowlist because delta-rs 1.0.2 refuses a write whose list names a list, map,
struct with a binary field or missing column. The property is set once and never changed: a
column added by schema evolution gets no statistics and logs nothing. Existing tables are
not altered and keep warning (`docs/troubleshooting.md`, the `RUST_LOG` filter). Tests
capture the delta-rs log on create, append, MERGE, schema evolution and a job run, write a
column of every kind, check file pruning on a listed column, and check that an older table is
left as it is and that a plain `deltalake.write_deltalake` appends to a new one.

A property can be changed on an existing table later (`DeltaTable.alter.set_table_properties`,
one metadata commit); it applies only to files written after the change, and earlier files
keep the statistics they were written with.
