## `src/orcapod/core/operators/filters.py` — `PolarsFilter` identity and nullability (ITL-828)

### PF2 — `PolarsFilter` carries every column through Polars and changes values
**Status:** open
**Severity:** critical
**Issue:** ITL-1296 (related: ITL-1284, ITL-1374)

`PolarsFilter.unary_static_process` builds a Polars frame of the whole table, filters it
and converts the result back to Arrow, then casts it to the input types. Every column goes
through Polars, also the columns the predicates never read, and Polars does not hold every
Arrow type exactly: a `date64` data column `[1, 86400001]` ms comes back `[0, 86400000]` ms,
with no error, and a `decimal256` column is reported to make Polars panic, which no caller
can catch. A filter must pass the rows it keeps unchanged.

**Deferred (developer, November 28, 2026):** "defer using polars filter and entirely focus on
filter for the users. For now I'd be even fine for PolarFilter to always throw a warning when
instantiated." The value fault is not fixed. Instead:

- Building a `PolarsFilter` (the class, or `stream.polars_filter(...)`) issues
  `PolarsFilterWarning` (`orcapod.errors`, a `UserWarning`) every time, not once per process:
  it names the fault and `Filter` as the operator to use. It is shown at the user's line
  (`warning_utils.warn_at_frame`) and is in addition to the once-per-process
  `ProvisionalHashWarning`, which is unchanged. The warning enters no identity; no golden
  value moves.
- Every route that builds one warns: `PolarsFilter.from_config`,
  `serialization.resolve_operator_from_config`, and `PipelineJob.load` / `Pipeline.load`,
  once per saved `PolarsFilter` node at every load. A saved filter a load cannot rebuild (a
  predicate that is not an expression) is kept read-only and its constructor never runs; the
  load warns for it too (`graph.py`, beside the provisional warning of such a node), so
  loading is uniform. One helper issues the warning, `filters.warn_polars_filter_values`.
  Running or saving a job does not warn.
- Tests that build a `PolarsFilter` for another purpose ignore the warning with a per-file
  `pytestmark` and a reason; `tests/test_core/operators/test_polars_filter_warning.py`
  asserts it on every route. No pytest configuration ignores it.
- `Filter` (ITL-1374) is the filter the documentation presents. It chooses rows with an
  Arrow mask and takes them from the input table (`filter_mask.filter_table`); it was probed
  for this fault and is exact. The probe is kept as
  `tests/test_core/operators/test_filter_exact_values.py`: a `date64` off midnight,
  `time64[ns]` below a microsecond, a float32 signaling NaN, `-0.0`, `decimal128` and
  `decimal256` at full precision, logical types, strings and binaries of both widths, lists
  and structs, each as tag, data and data-tag, in two table arrangements, on the sync path,
  the row channel path and in a job run by either orchestrator.

Still open: `PolarsFilter` itself (Polars decides which rows are kept, the rows are taken
from the Arrow table), or its removal.
