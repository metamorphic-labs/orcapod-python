## `src/orcapod/databases/` — column order of appended tables

### CO1 — Databases refuse an append whose columns are in another order than the stored or pending table
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1367

An append whose columns were the table's columns in another order was handled differently
by each database (measured on main 321284ae: two rows `rid, a, c, b`, then two rows
`b, c, rid, a`, with `a` and `c` both `int64`). The in-memory database refused it, after a
flush and within one pending batch. Delta matched it by name after a flush and refused it
within a pending batch. The connector database over SQLite did the same as Delta. The
SpiralDB fake refused it in both cases. No database swapped values by position, but the
column order of a stored table was in effect part of its schema: a job node that produced
the same columns in another order than an earlier run, or than an earlier batch of the same
run, could not store them, although no hash depends on column order.

Live SpiralDB was measured (2026-11-22): it accepts a write in another order and matches it
by name, and it keeps a column order of its own whatever the order written: the key
columns in key-schema order, then the value columns sorted by name (code point: `B`, `C`,
`a`), struct children sorted by name too. The fake refused what SpiralDB accepts and kept
the written order.

**Fix:** one shared step, `databases/utils.in_held_column_order`. When rows have exactly
the held columns in another order, and each field equals the held field of its name, the
rows are put in the held order, by name. Equal is one rule (`_same_field`): the same type
at every depth in the large variants, a logical (extension) type equal only to its own
name and metadata at any depth, and no change the ITL-1334 append check reports
(`appended_field_change`: field metadata and nested field attributes). Names match exactly
(`a` and `A` are two columns). Anything else is left exactly as given, so each database's
own rule applies as before.

Where it runs, and against what:

- In-memory: when rows are queued, against the batch pending for the table, else the
  stored table (main refused both).
- Delta: when rows are queued, against the batch pending for the table only (main refused
  a permutation of a pending batch; a stored table already takes an append by name,
  through delta-rs). The pending batch is left exactly as main would hold it, so main's
  commit selection, schema handling and requeue run unchanged.
- The connector database (SQLite, PostgreSQL, SpiralDB): when rows are queued, against the
  batch it has pending only. Nothing about a stored table is trusted across calls: a flush
  looks the table up then (main's own lookup), checks the queued rows by exact name and
  type as main does, and only then puts them in the stored order (the flush compares the
  connector's column info, which carries no field metadata: a column with field metadata
  stays in its queued order, which SpiralDB, the connector that keeps field metadata,
  matches by name itself); a read that combines stored and queued rows matches them to
  the rows it reads, and takes a column nullable when either side declares it nullable
  (PostgreSQL reads its key back NOT NULL; arrays re-wrapped, never cast). A point
  lookup of a queued row answers from memory, as main does.

Pre-existing on main and out of scope: two Delta writers appending one new record id can
both store it through the fast-path append (ITL-1377).

A table keeps the order its database gave the first write (SpiralDB: its own order). The
SpiralDB fake now mirrors SpiralDB at the top level: it matches a write by name and stores
the key columns, then the value columns by name. Tests:
`tests/test_databases/test_append_by_name.py`; live: `TestColumnOrderLive` in
`tests/test_databases/test_spiraldb_connector_integration.py`.

Pre-existing on main and equal here, not changed: another connection that changes a SQLite
table between the flush's check and its write (a DDL in that window) is not seen; a rename
of `a` to `A` then stores the value under `A`, since SQLite resolves names without case, as
on main. Through `ExtensionAwareDatabase`, rows of another logical type over the same
storage type in the SAME column order are accepted and read back as the held logical type
(ITL-1371 now refuses them, in either column order, wherever the held identifier is known:
not over a Delta column with no identifier and no recorded Arrow type, such as one written
from a dictionary of extension values, where the identity rule abstains; ITL-1372).

Not covered: the order of a struct's fields (a struct with its fields in another order is
another type here, and the fake keeps struct children as written): ITL-1368. A new table
is written in a canonical order since ITL-1370 (CO2), decided from
`docs/dev/specs/itl-1367-stored-column-order.md`.
