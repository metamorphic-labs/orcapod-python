## `src/orcapod/databases/` — column order of appended tables

### CO1 — Databases refuse an append whose columns are in another order than the stored or pending table
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1367

An append whose columns were the table's columns in another order was handled differently
by each database (measured on main 321284ae: two rows `rid, a, c, b`, then two rows
`b, c, rid, a`, with `a` and `c` both `int64`). The in-memory database refused it, after a
flush and within one pending batch. Delta matched it by name after a flush and refused it
within a pending batch. The connector database over SQLite did the same as Delta. The
SpiralDB fake refused it in both cases. No database swapped values by position, but the
column order of a stored table was in effect part of its schema: a job node that produced
the same columns in another order than an earlier run, or than an earlier batch of the same
run, could not store them, although no hash depends on column order.

Live SpiralDB was measured (2026-11-22): it accepts a write in another order and matches it
by name, and it keeps a column order of its own whatever the order written: the key
columns in key-schema order, then the value columns sorted by name (code point: `B`, `C`,
`a`), struct children sorted by name too. The fake refused what SpiralDB accepts and kept
the written order.

**Fix:** one shared step, `databases/utils.in_held_column_order`, in every database
(in-memory, Delta, `ConnectorArrowDatabase` for SQLite, PostgreSQL and SpiralDB). Rows with
exactly the held columns in another order, each with the held column's type (compared in
the large variants, a logical type by its storage type) and the same logical type (an
extension type's name and metadata, or the `ARROW:extension` annotation of a field held
as its storage type), are put in the held order, by name. Names match exactly (`a` and
`A` are two columns). Anything else keeps the database's own rule: a column added or
missing, a type or logical type that differs, a name that repeats exactly.

Where the step runs, and against what:

- In-memory and Delta: when rows are queued, against the batch pending for the table,
  else the stored table, after the checks on the rows alone and, in Delta, after
  duplicates are dropped, before the checks that compare the rows with the held columns.
  A Delta batch holding rows reordered this way is committed by MERGE (insert-if-missing),
  the commit main chose for rows in another order; the marker is set only for rows
  actually queued and leaves with them.
- The connector database: when rows are queued, only against the batch this handle has
  pending for the table. Nothing about a stored table is trusted across calls (another
  connection may rename, add, drop, retype or create a column again in between): a flush
  looks the table up then, checks the queued rows against it by exact name and type as
  main does, and only then puts them in the stored order; a read that combines stored and
  queued rows, and a point lookup of a queued row, match them to the stored table read
  then.

A table keeps the order its database gave the first write (SpiralDB: its own order). The
SpiralDB fake now mirrors SpiralDB at the top level: it matches a write by name and stores
the key columns, then the value columns by name. Tests:
`tests/test_databases/test_append_by_name.py`; live: `TestColumnOrderLive` in
`tests/test_databases/test_spiraldb_connector_integration.py`.

Found in review, pre-existing on main and not changed here: through
`ExtensionAwareDatabase`, rows of another logical type over the same storage type, in the
SAME column order, are accepted and read back as the held logical type.

Not covered: the order of a struct's fields (a struct with its fields in another order is
another type here, and the fake keeps struct children as written): ITL-1368. A canonical
order for a new table is a proposal awaiting the developer's decision:
`docs/dev/specs/itl-1367-stored-column-order.md`.
