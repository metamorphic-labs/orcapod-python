## `src/orcapod/core/data_function.py`

### OK1 — The order of `output_keys` is in no identity
**Status:** resolved (decided: the identity is right as it is; the cache check is ITL-1253)
**Severity:** high
**Issue:** ITL-1244

Two pods of one function whose `output_keys` differ only in order (`['sum', 'product']`
against `['product', 'sum']`) have one uri, content hash and pipeline hash: the uri holds
the hash of the output schema, and a schema hash sorts its field names. A job with the
second order on the database of a job with the first is served the first one's stored rows,
so the values appear under the other names. Found by the several-item test audit
(ITL-1236).

**Fix:** Decided by the developer (November 17, 2026): the outputs of a function are a set of
named, typed values, so the uri holds the order-free output schema, as before. A swap of
differently typed keys changes the schema and so the uri; a swap of same-typed keys does not.
The positional mapping belongs with the body: a swap among same-typed outputs changes what
the function computes and needs a major version bump, as a body edit does (the uri holds
only the major version, so a minor bump would serve the earlier order's stored values while
a cache hit is not checked, ITL-1253). No code changed. The
behaviour is pinned in `tests/test_core/function_pod/test_output_keys_identity.py` (two and
three keys in every order, sync and async, in memory and in a job on an in-memory and a
Delta database, plain tags and data-tags; input parameters pinned as outside the uri) and
documented in `docs/concepts/identity.md` (*Change detection*). A cache hit whose stored
function variation data differs from the current function is still served silently: that
check is ITL-1253 (a strict xfail test states it).
