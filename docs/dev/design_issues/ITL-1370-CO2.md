## `src/orcapod/databases/` — column order of appended tables

### CO2 — A stored table's column order followed whichever write created it
**Status:** resolved
**Severity:** low
**Issue:** ITL-1370

Each stored table kept the column order of its first write, and each writer built its rows
its own way: the five table kinds disagreed (a cached source put data before its system
tags, an operator cache after them), the user columns followed the declared tag order,
which the rule that order never counts allows only as presentation, and SpiralDB stored
none of these orders (it keeps the key columns, then the value columns by name). Readers
presented a stored table in its stored order, so what a user saw depended on how the
table's first write happened to be built.

**Fix:** a new table is written in the canonical order: the record id, then every other
column by name (code point), by the shared step every database calls
(`databases/utils.canonical_column_order`, from `in_held_column_order` when nothing is
held). It is SpiralDB's own order. A table that exists keeps its order and takes appends
by name (CO1, ITL-1367). Every reader of stored rows presents them in its own layout through
one helper, `arrow_utils.in_presented_order`: `CachedSource`, `DerivedSource`, the function
node's stored view (`_presented_layout`), the operator node's stored read, the result cache
(`result_table_layout`), the status and log observers and `ObservabilityReader`. No hash,
record id, stored path or layout version moves (golden check; and
`tests/test_databases/test_canonical_stored_order.py` runs one job writing every table
kind with the canonical order switched off and on and compares content and pipeline
hashes, paths, record ids and every reader). Decision and evidence:
`docs/dev/specs/itl-1367-stored-column-order.md`.
