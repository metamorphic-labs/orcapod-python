## Cross-cutting

### MT1 — `MapTags(drop_unmapped=True)` predicted no system-tag columns
**Status:** resolved
**Severity:** high
**Issue:** ITL-1363

`MapTags.unary_output_schema` kept a tag-schema key only when it was a key of `name_map` or
`drop_unmapped` was false. Under `columns={"system_tags": True}` or `all_info=True` the tag
schema holds the system-tag columns, which no `name_map` names, so the prediction left them
out while the computed table keeps them: a node, a stored table or a downstream operator
that reads the prediction expects columns the rows do not match. `MapData`'s prediction
filtered its data schema the same way (by the names of `name_map`, not by the input's user
columns); no column the data schema can hold today was affected, but the rule was the same.
The ITL-1135 sweep missed it: it had no `drop_unmapped` step.

**Fix:** one rule, `mappers._plan_group`: only a user column (a tag, or a data column that
is not meta) is renamed or, with `drop_unmapped`, dropped; a system tag, source info, the
context or a meta column never is. `MapTags`' and `MapData`'s predictions and
`MapColumns._plan` use it. No row, column, hash or stored path changes. The ITL-1135 sweep
(`tests/test_pipeline/test_zero_row_column_order.py`) has `drop_unmapped` steps for the
three mappers and `MapColumns` steps, and
`tests/test_core/operators/test_mapper_schema_prediction.py` checks every column
configuration over every arrangement of a source with three tags and three data columns,
on the sync and the async path.
