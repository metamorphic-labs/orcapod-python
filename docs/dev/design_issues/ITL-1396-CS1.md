## `src/orcapod/core/sources/cached_source.py`

### CS1 — A cached source presented two rows for one record id after its source changed a value
**Status:** resolved
**Severity:** high
**Issue:** ITL-1396

A `CachedSource` stores each delivered row under the hash of the whole row and keeps every
row it ever stored. When the wrapped source later delivered another value under a record id
the cache held (a CSV file whose `(s1, 2)` row went from 2.0 to 2.5, with
`record_id_columns=["subject", "session"]`), the new row was stored beside the old one and
the cached source presented both: one record id, two rows, no error, and every downstream
node stored results for both. A source with key columns refuses a repeated key when it is
built, so the cache was the one route to that state. The same happened for a source without
key columns, whose record id is the row's position (`row_1` twice).

**Fix:** (developer, November 28, 2026: refuse, and record when each row was written) a
delivery holding a row whose record id the cache holds under another `_record_hash` is
refused before anything is written (`CachedSourceChangedRowError`, an
`InputValidationError`, from `CachedSource._require_no_changed_rows`), naming the source
id, the first five record ids and the count, with the remedy: a new source id for changed
data, or a new cache. Content is compared by the record hash the cache already stores (the
whole stored row: tags, data, system tags, source-info tokens); no new hash. One rule for
every wrapped source: with positional record ids a reorder or a row inserted before the last
is refused too, and an append is accepted. The same row again writes nothing; a row under a
new record id is added. The refusal is a decided rule, not a stopgap.

The check finds the generated record-id column in the wrapped source's declared fields
and reads it by name. If the stored schema uses a different generated name, the check
resolves the stored pair from its own schema and compares the record-id values.
Custom system tags still contribute to the row hash.
A stored provenance pair can retain its generated role even when a new
declaration uses its names for custom provenance. When more than one pair is
present, the check uses the stored payload fields to recover the generated
name, so adding a nullable column to the reader does not block a clean read.
A plain derived source has no generated record id and deduplicates by record hash.
Ingestion refreshes the cache table to see rows already committed by another writer.
Nested cache wrappers, including those linked by a bound source proxy or a keyed
`DerivedSource(tags_as_data=...)`, check the delivery at each level before writing any
rows. A changed-row refusal during a freshness check fails a sync or async run and
continues to do so on retry while the conflict remains. Delta cache previews keep nullable
columns when an append omits them, filling the new rows with nulls as Delta does.

The cached-source table (`sdb_v2`, unreleased, so no new layout version) gains
`__recorded_at` (`timestamp[us, tz=UTC]`, non-nullable): when the cache wrote the row, one
time per write, appended after the record hashes (in no hash, record id or token) and
dropped by every read. Nothing selects by it. It exists so that a later mode, "present the
latest row of a record id by its recorded-at time", can be offered without a new layout.
An earlier prerelease table without the column is refused with a rebuild message.
SQLite refuses the timestamp at construction because its connector cannot store it.

**Read side:** (developer, November 28, 2026: "(b) for now") a cache table that already
holds two contents for one record id (two writers that both passed the check before either
wrote, or a table written by hand) is refused whenever it is read, with the same
`CachedSourceChangedRowError` ("the cache ... holds N record ids with more than one
content"), naming the source id, the first five record ids and the count. One rule,
`CachedSource._require_one_content_per_record_id`, on record id and the stored
`_record_hash` (the same row stored twice is not a conflict), runs in
`_read_cache_table` for every cache read. Each read refreshes the database handle.
Freshness checks validate the cache before comparing the wrapped source's modified time.
When the source holds no rows, `head()` projects the record ids and hashes, with the data
context as a filter. The notebook preview displays the error. A reloaded source with an
unbound proxy resolves an ambiguous record-id column from the saved user-facing keys and
the stored Arrow schema, using the same schema hash as the source builder. A source
object holding rows it already read shows them, on a full read and on `head()` alike,
without reading the cache again. A cached source therefore never presents two rows for one
record id. The handling of several held versions of one record in
`pipeline/provenance.py` is no longer reached through a cached source; it is left in place.

Review fixes on the nested-cache preview: what a read gives after an append is asked of
the store (`ArrowDatabaseProtocol.preview_appended_rows`, implemented by every database
class; the extension-aware wrapper delegates), never decided from the store's class, and
the stored rows are not held to the source's declared types before a delivery that may
evolve the table (a new nullable column or struct child) is written; the rows read back
after the write are checked.

**Open:** the simultaneous-writer race itself: two writers can still both pass the check
and both write. Its result is refused at the next read. Resolving two contents for one
record id by time (`__recorded_at`) or another tie-breaker instead of refusing is ITL-1592.

The cached sources of one job are checked one by one. When two cached sources feed a job
and one is refused, another that accepted its delivery may already have written it (and,
on the async path, its branch may have computed for the new rows) before the run fails.
The rows written are that source's own valid delivery. "Nothing is written at any level
until every level passed" covers the nested caches of one read, not sibling sources.
`test_cached_source_conflicting_cache.py` pins the case.

A positional `DerivedSource(tags_as_data=...)` interposed between caches assigns record
ids from its origin's database read order. A Delta append can change that order, so the
origin may commit the append before the enclosing cache refuses the changed positional
record. The strict xfail in `test_cached_source_changed_rows.py` pins the case.
