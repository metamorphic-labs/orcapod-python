## `src/orcapod/core/nodes/source_node.py`

### RT4 — A loaded job keeps a data-tag column's pending type for one role only
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1200 (found on ITL-1023, PR #342)

A loaded job keeps a slot column's type as pending when it names a user class not registered in the process (`_keep_saved`), and restores it when a source of that class is bound (`_restore_pending_types`). Pending types are keyed by column name only, so for a data-tag (one name in the tag and the data schema) the data entry replaces the tag entry. After binding, the tag schema still holds the saved text as a `str`, and `_fit` can refuse a matching source with a type-mismatch message instead of the unregistered-type message. Readers to change: `_restore_pending_types`, `_take_saved_state_of`, `_pending_nullable_columns`, the `_fit` message lookup. Reported by CodeRabbit on PR #342; ITL-1200 fixes it.

**Fix:** PR 454 (ITL-640). A loaded slot keeps no per-column pending state any more: while
unresolved, its saved Arrow type texts are the one source of its types, and one transition
(`SourceNodeBase._resolve`) derives the Arrow pair and both Python schemas, tag and data, from
them together. A data-tag column resolves in both roles at once. Test: the `datatags` layout of
`tests/test_pipeline/test_loaded_slot_unregistered_class.py` (the class column `t` and an
`int16` column `k` as data-tags; register and bind before and after saving again, by
`Pipeline.save` and `PipelineJob.save`, and reloaded; a widened `k` refused). Its ten cases
fail on 73652317 with the refusal this entry describes and pass on the fix.
