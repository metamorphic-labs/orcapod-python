## `src/orcapod/databases/delta_lake_databases.py`

### CW1 — Two writers committing the same new record id to a Delta table both commit
**Status:** resolved
**Severity:** high
**Issue:** ITL-1377

`DeltaTableDatabase` decided which pending ids were new against the version it loaded for
a commit, and committed a batch of new ids by a plain WRITE (append). Another writer (a
second handle, or another process) could commit the same id between the load and the
append. A Delta append never conflicts with a concurrent append, so both commits
succeeded and the id was stored twice. This happened with `skip_duplicates` true and
false, in every `schema_handling` mode, and in any column order. Only a batch that took
the MERGE path (a stored id among its ids) was protected. Two writers creating a new
table at once had the same problem (ITL-1384): the later `mode="overwrite"` create
removed the earlier writer's rows.

What deltalake offers was measured, not assumed:
- None of these makes an append conflict: `CommitProperties(max_commit_retries=0)`,
  application transactions, an overwrite with a predicate on the binary id, or the
  table-level options of `write_deltalake`. They all commit on top of the concurrent
  commit.
- Only a MERGE fails (`CommitFailedError`) when another writer added rows after its load.

**Fix:** every commit to an existing table is a MERGE that inserts only the ids the
table does not hold (`_commit_once`), with `streamed_exec=False`.
- **Retries.** On `CommitFailedError` the flush loads the table again, decides against
  it and retries, at most `_COMMIT_ATTEMPTS` (200) times, with a random wait of at most
  0.5 s. After the last attempt it raises the conflict, as before.
- **Creating a table.** A new table is created with `mode="error"` and no commit retry,
  so a create that lost the race fails and is retried as a MERGE. Without that, deltalake
  1.6 commits the losing create on top of the winner's.
- **Duplicates.** The later writer leaves an id the earlier one stored, and so stores
  each id once. ITL-1386 refuses an id visible at add time in strict mode. A key
  committed by another writer after the add-time check is still skipped at flush.
- **Backticks.** delta-rs cannot MERGE a table with a top-level column whose name holds
  a backtick, so such a column is refused (ITL-1375).

**Cost.** delta-rs's insert-only MERGE reads every stored row in full: it is a full outer
join, and the binary id column has no file statistics, so no file is skipped. A commit
therefore costs time in proportion to the table's size. ITL-1403 (deltalake 1.6.6) made
that MERGE 2 to 8 times faster. ITL-1406 lists stored layouts that would let it skip
files. Commit in batches (a job's default of 100 rows per commit) rather than per row,
above all to tables holding large values.
