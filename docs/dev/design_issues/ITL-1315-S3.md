## `src/orcapod/core/sources/`

### S3 — A `CSVSource` lost its explicit schema when reloaded from its configuration
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1315

`CSVSource.to_config()` left out the `schema=` the source was built with, so
`CSVSource.from_config()` (and a job loaded with `PipelineJob.load`) inferred the types from
the file again. Measured in the ITL-1311 inventory: file `k,x\n1,10\n2,20\n`, schema
`k: int64 not null`, `x: int64` nullable, `tag_columns=['k']`; after the reload the source id
was the same, `x` read as `int` instead of `int | None`, and the content hash and pipeline
hash differed. A width (`int32`) and a string of digits were lost the same way. The
inventory found no other source with the defect: `DeltaTableSource`, `SQLiteTableSource` and
`PostgreSQLTableSource` take no schema argument, and `DataFrameSource`, `ArrowTableSource`,
`DictSource` and `ListSource` cannot be rebuilt from their configuration at all.

**Fix:** `to_config()` writes `"schema": {"columns": {...}, "nullable": [...]}`, the Arrow
type text the saved schemas already use (`serialize_schema`, which carries nested field names
and nullability) plus the nullable top-level names (as the saved `output_schema` records
them), through `pipeline/serialization.serialize_arrow_schema`; `from_config()` restores it
(`deserialize_arrow_schema`) and passes it to the constructor. The writer reads its entry
back and refuses (`ValueError` naming the field) any schema it would not restore exactly,
metadata compared; `PipelineJob.save` adds the source's slot and writes nothing. A source
without `schema=` writes no entry, and a configuration without one loads as before, so the
job and pipeline file formats keep their version (an added optional source-config key, as
SpiralDB's `where`). No hash moved.

Arrow metadata is refused, not saved (coordinator decision for ITL-1315, option A of three): nothing in a saved file serializes Arrow metadata, and the type text cannot carry the
metadata of a nested field at all, so saving it would add a second format piece to carry
into the 0.4.0 freeze for a rare case; dropping it silently would lose what the user gave.
Limit: a file written with the entry and read by a library without this fix loads with the
types inferred again, as before the fix.
