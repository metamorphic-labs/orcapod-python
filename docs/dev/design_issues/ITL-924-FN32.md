## `src/orcapod/semantic_types/canonical_order.py` — dict and set values in canonical order

### FN32 — Python floats were narrowed silently into a `float32` column, and dict keys that collide after narrowing lost an entry
**Status:** resolved (columns declared `np.float32` in a Python schema); Arrow-declared `float32` / `float16` columns remain
**Severity:** high
**Issue:** ITL-924

A column declared `np.float32` let Arrow narrow a Python `float` into it with no sign: `1e-50`
was stored as `0.0`, `0.1` as `0.10000000149011612`. With `dict[np.float32, V]` the keys
`1e-50` and `2e-50` are distinct Python floats, so they passed the duplicate-key check of
ITL-905, which compared the keys as given; Arrow then stored two entries with the key `0.0`
and reading the value back dropped one. A `set[np.float32]` stored two `0.0` elements the same
way.

**Fix:** the developer ruled (November 28, 2026) against any check of each value ("rather just
raise warning about it once and move past it"). The converter of a narrower float type
(`semantic_types/float_narrowing.py`) returns every value as given, so Arrow converts it as
before, and issues one `ValueConversionWarning` per process and declared type the first time
it is given a wider float, decided from the value's type and the declared type only. Dict keys
and set elements are compared as they are stored (`stored_key_converter` narrows a wider float
key before the ITL-905 check, in the converter and in `canonical_python_value`), so colliding
keys raise `CanonicalOrderError` naming the column and both given keys. The function-output
check takes its float-narrowing predicate from the same module, and an accepted narrower
output (`np.float16` for `np.float32`) is normalized to the declared type instead of a Python
`float`, so it is not reported as narrowed. No stored value and no hash changes.

Not covered: a narrow float type known only from an Arrow schema. Arrow to Python maps every
float width to `float`, so `Datagram.update` on a table-backed row and `DictSource` with an
Arrow `data_schema` holding `float32` or `float16` still narrow silently and still store
colliding keys. `np.float16` has no Python-to-Arrow mapping.
