## `src/orcapod/semantic_types/canonical_order.py` — dict and set values in canonical order

### FN32 — Python floats were narrowed silently into a `float32` column, and dict keys that collide after narrowing lost an entry
**Status:** resolved for Python-declared float32 inputs within the scope below
**Severity:** high
**Issue:** ITL-924

A column declared `np.float32` let Arrow narrow a Python `float` into it with no sign.
For example `1e-50` was stored as `0.0`, and `0.1` as `0.10000000149011612`.
Distinct keys in a `dict[np.float32, V]` or elements in a `set[np.float32]` could become
equal in Arrow and lose an entry on readback.

**Fix:** Issue one `ValueConversionWarning` per process and declared type when a
caller supplies a wider float to a Python-declared float32 field. The warning
uses the value's type. The converter still passes the value through to Arrow.
Forked children start with fresh warning state. An active error filter applies
even after a previous warning.

For supported keys and elements, the canonical sorter checks the rounded values
for collisions and reports both original inputs and their shared stored value.
The legacy ranks still determine key order and Arrow receives the original
converted inputs. Validated function outputs retain the existing conformance
and normalization rules. The input diagnostics are suppressed when converting
those outputs or rebuilding a datagram from stored data.

**Known limitations:** Updates after materialization use the context's table
converter with the existing Arrow schema, including when the original datagram
had a Python schema. Plain float widths in that conversion and in Arrow-declared
sources map to Python `float`, so those paths can still narrow silently and
store collisions. NumPy scalar subclasses whose key conversion can call custom
`__float__` methods retain the legacy collision behavior.
