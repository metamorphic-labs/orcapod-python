## `src/orcapod/pipeline/job.py` — reading a loaded `PipelineJob`

### AO1 — A loaded job could run MergeJoin or SemiJoin with its inputs swapped
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1417

A saved job listed an operator's inputs only through the edge list, whose order follows
the order the steps were recorded in, and both loaders (`Pipeline.load`, `PipelineJob.load`)
gave the operator its inputs in that order (the job loader through the hash graph's
predecessors, which a copy reorders again). With another step over the second input recorded
first, a loaded `MergeJoin(left, right)` ran as `MergeJoin(right, left)`: a job run with
`load_only=True` returned `[[100, 1], [101, 2]]` where the live job had `[[1, 100], [2, 101]]`.
`SemiJoin` kept the wrong side. Commutative operators (`Join`, `Rejoin`) were not affected.
Found while building ITL-1387.

**Fix:** every saved operator node lists its inputs' keys in argument order under `inputs`
(format 0.4.0, added within the version), and both loaders build an operator's inputs from
that list. A file saved before has no list: an operator over two or more different inputs
loads only when it is positively known to be commutative (available, and its
`argument_symmetry` on the rebuilt inputs is a flat `frozenset` of them); anything else is
refused at load (its order cannot be known). Review of the PR (Codex): the check asks the
symmetry of the rebuilt streams, not hash strings; a nested group and a read-only operator
are refused; a read-only node keeps its inputs.
`tests/test_pipeline/test_loaded_argument_order.py`.
