## `src/orcapod/core/sources/`

### S4 — A `CSVSource` with an explicit schema reads inferred types first: `"007"` is stored as `"7"`
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1322

`CSVSource._read_table` reads the file with pyarrow's inferred column types and casts the
table to the `schema=` the source was built with afterwards. A column declared as a string
whose text looks numeric is read as a number first, so the text `007` is read as `7` and
stored as `"7"`: the value in the file is lost, although the user gave its type. Leading
zeros (identifiers, postal codes), a trailing `.0` and exponent forms are affected. Found
while fixing the config reload of an explicit schema (ITL-1315).

Passing the declared types to the reader (`pyarrow.csv.read_csv` with
`ConvertOptions(column_types=...)`) would read the text as given. The fix changes the stored
values, and so the row hashes, of an existing source of this kind (no hash algorithm and no
golden value: the golden CSV fixtures use inferred types), so the developer decides when.

**Fix:** `csv_source._read_declared` reads every column with its declared type
(`ConvertOptions(column_types=...)`; a logical type as its storage, wrapped by the final cast;
`float16` and `decimal256` as text with a checked cast; a nested type refused naming the
column), then gives the table the schema exactly. Nulls follow option C (developer decision,
November 21, 2026): in a string column only an unquoted empty field is null (a quoted `""` is
`""`, `NA` and `null` are text); other columns keep pyarrow's null markers. pyarrow's null list
applies to a whole read, so a file with both kinds of columns is read twice with one set of
read and parse options, the string columns the second time, and the row counts are compared.
The schema must name every column of the file in order (as the cast required before). No hash
algorithm and no golden value moved; stored values of such sources change where the text was
altered before.
