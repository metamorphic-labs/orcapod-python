## `src/orcapod/core/operators/merge_join.py` — Arrow types

### MJ3 — `MergeJoin` changed values and misaligned its lists by sorting Python values
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1281 (related: ITL-1241, ITL-1243, ITL-839, ITL-1250, ITL-1284)

`MergeJoin` carried every column through a Polars join and built each merged column from
Python values (`to_pylist`), sorting each row's two values per column. A value with no exact
Python form changed on the way: a `time64[ns]` value lost its nanoseconds, a `date64` value
off midnight came back at midnight, a float32 signaling NaN came back quiet, and a
`decimal256` column made Polars panic. Each column was sorted on its own values, so with two
colliding columns one row could hold `x = [3, 5]` (from B, A) beside `y = [1.0, 2.0]` (from
A, B): the lists were not parallel by origin row. A null among the values (ITL-1243) or a
struct value (ITL-839) could not be sorted and raised `TypeError`, and tied values kept
argument order (ITL-1241).

**Fix:** `MergeJoin` is ordered, not commutative (developer, November 19, 2026): its identity
holds its inputs as a tuple, each input's system-tag columns end in its argument index, and a
merged list is `[first argument's value, second argument's value]` with its source-info list
in the same order. Nothing is sorted. Polars only matches prepared keys and row numbers
(`Join`'s `_inner_join`, `arrow_keys`); every output value is taken from the input tables
and the lists are built from their arrays (`arrow_utils.aggregated_list_array`), so every
value is the input's, bit for bit, for every Arrow type. The 21 golden entries of
`pipeline:merge_join` and the `merge_join.*` entries of `pipeline:join_key_nullability`
moved, as approved by the developer. Tests:
`tests/test_core/operators/test_merge_join_values.py`.
