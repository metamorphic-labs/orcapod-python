## `src/orcapod/core/streams/`

### GW1 — Defining stacked split-and-join stages took time exponential in the stages
**Status:** resolved
**Severity:** high
**Issue:** ITL-1111

A pipeline whose every stage splits a stream into two branches and joins them again took
about 4x longer to define per stage (9 stages: 13 s, no row computed), as streams and inside a
`PipelineJob`. Three walks asked a shared upstream once per path instead of once:
`DynamicPodStream`, `FunctionPodStream`, `FunctionNode` and `OperatorNode` predicted their
output schema from their upstreams on every call, and `Join.output_schema` asks each input
several times (`keys`, `output_schema`, the system-tag schema); `StreamBase._schema_requires_io`
(`head()`, the notebook preview) recursed into every upstream path; and `process` / `__call__`
of operators and function pods formatted the input streams, whose `repr` nests every upstream,
into an f-string debug log on every call, even with debug logging off.

**Fix:** `StreamBase._memoized_output_schema` keeps the predicted `(tag_schema, data_schema)`
per normalized `ColumnConfig` (an unhashable config is predicted every time) on the four
owners; each states what its prediction depends on (the pod and the upstreams' schemas and
pipeline hashes, never rows). The node `upstreams` setters and `PipelineJob.bind(sources=...)`
clear it. `_schema_requires_io` visits each upstream once per call and keeps nothing, because
a polling source's answer changes once it has polled. The debug logs take `%s` arguments, and the `repr` of `DynamicPodStream`, `OperatorNode` and
`FunctionNode` names each upstream by class and label only (`short_stream_repr`), so printing
a stream or logging at debug level is bounded too.
Call-count tests over 20 stages: `tests/test_pipeline/test_graph_walk_cost.py`.

Assigning `SourceJobNode.bound_source` directly or setting a node's `upstreams` clears no memo
of downstream nodes. A bind preserves the slot's schema (ITL-1112), and the `upstreams`
setter now refuses a replacement with another schema (ITL-1125). Each join keeps both inputs'
system-tag columns, so their number doubles per
stage (2 ** (stages + 1)), which is the width of the output, not a walk.
