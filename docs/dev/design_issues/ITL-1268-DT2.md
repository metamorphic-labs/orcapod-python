## `src/orcapod/semantic_types/universal_converter.py`

### DT2 — a `datetime` output lost its nanoseconds silently, and a naive one failed without saying why
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1268

`-> datetime` declares an instant, `timestamp[us, tz=UTC]`, and every Arrow timestamp type
reads as `datetime`; a function receives a `pandas.Timestamp` from a `timestamp[ns]` column.
Two defects, measured on `main` on 2026-11-21:

- A value with a part below one microsecond (`2023-11-14 22:13:20.123456789+00:00`) was
  stored as `...20.123456`, silently. That held for a function output (sync, async, plain
  pod, job node, inside a list or a dict) and for a `DictSource` declared `datetime`.
- A naive value returned by a function failed every row with "returned datetime.datetime for
  output 'y', which is declared datetime.datetime: ValueError". `_convert_outputs` showed
  only the converter error's class name, since that error's message holds the value. A
  source over Python values gave the clear strict time zone policy message.

**Fix:** one rule, `universal_converter.storable_instant`, which the converter's `datetime`
conversion calls for every path. A naive value raises `NaiveDatetimeError` (strict
policy); a value with a part below one microsecond raises `SubMicrosecondDatetimeError`.
Both are `UnstorableDatetimeError`s (`ValueError`), whose `reason` and `hint` name no
value; their message adds it. `_convert_outputs` shows the reason and hint in the
`OutputTypeError`, not chained, so the value stays out of the output error. The mapping is
unchanged (developer, November 21, 2026): no hash, golden value or stored type moves.
Declaring an unzoned or nanosecond output is ITL-1325.
