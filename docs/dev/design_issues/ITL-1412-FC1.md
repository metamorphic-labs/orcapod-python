## `src/orcapod/databases/` — function result and pipeline commits

### FC1 — Function pipeline records could outlive their discarded results
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1412

A failed result write left pipeline records pending. A database-wide flush after the
failure could commit those records even when the result still failed or the database
had already dropped it. With separate result and pipeline stores, a successful async
branch could also publish its sibling's pipeline records before the sibling's result
table had committed.

**Fix:** A pending pipeline record follows the commit attempt for its referenced
result. The database keeps the record in its normal readable queue while the attempt
is pending, makes it eligible for publication after success, and immediately withdraws
it on failure. Where a store supports scoped flushes, a function node flushes the
result and pipeline tables individually.
Nodes that share a physical table can still publish ready rows together. The
dependency state is held in memory and adds no columns or changes to stored identities.

Each guarded record takes one dependency reference and one entry in the reverse
lookup. A flush checks just its queued dependencies and partitions the Arrow batch
only when some rows must wait. A failed write removes its dependent records by ID
and leaves other pending rows intact. Result retries may still store results that
were buffered, and the next run can reuse those durable results to write new records.

In-memory tables use the same queue dependencies. A separately attached in-memory
result table is promoted at the node's batch boundary before publishing references
to it. Previously it stayed pending. Reads of the pending and promoted rows
return the same records. A no-op pipeline store leaves a separate in-memory result
table pending because it has no references to publish.

A no-op result database is an explicit discard. Its function nodes still write their
pipeline records for processed inputs, as before. Those records refer to output
that was never stored.

The result-first guarantee applies when both stores offer the optional
`ResultCommitGuardingDatabaseProtocol`. It defines `pending_result`, which returns
the result's commit token, and `guard_record`, which binds a queued pipeline record
to that token. `DeltaTableDatabase`, `InMemoryArrowDatabase` and
`ConnectorArrowDatabase` support it, and `ExtensionAwareDatabase` forwards it
when its underlying database does. `NoOpArrowDatabase` participates as the
explicit discard described above. A database implementing only
`ArrowDatabaseProtocol` still uses the original unguarded writes and flush cadence.
