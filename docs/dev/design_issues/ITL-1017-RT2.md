## `src/orcapod/core/data_tags.py` — data-tags workshop slice (ITL-1023)

### RT2 — A nested merged source-info token enters the next merge with its label
**Status:** resolved
**Severity:** low
**Issue:** ITL-1017

A value merged from several equal elements carries one source-info token, at first
`merged:source_fold_v1:<hex>` (`arrow_utils.fold_source_info_tokens`: SHA-256 of the canonical JSON
array of the sorted member tokens). A member can itself be a merged token (grouping a grouped stream,
a join after a group-by), and it enters the preimage as it is, label included. The workshop slice
accepts this on the precedent of source ids: a token is an identifier, and default source ids built
from a hash (`derived:<label>:<hex>`) are already used as they are inside source-info values and inside
`fold_system_tag_values`. The alternative is to feed a nested merged token's bare hex with a structural
marker (for example `{"merged": "<hex>"}`), which keeps every label out of every preimage but makes the
fold parse its members. Not frozen before v0.4: the developer decides. A related point for ITL-1019:
`OperatorNode` hashes a stored row with its source-info columns (`_record_hash`), so once streams with
data-tags can be stored in an operator node, a change of a group's membership moves that row's dedup key.

**Fix:** decided by the v1 hash definition (ITL-1154, developer, November 16, 2026): a hash fed
into another hash carries its label, so a nested merged token entering the next merge with its
label is the rule, not an exception. In the ITL-1154 refresh of the slice the token became the
merging operation's fold (`fold_system_tag_values`): `group_v1:<hex>` for a `GroupBy` key (members
in member order) and `join_v1:<hex>` for a `Join` key (members sorted); `fold_source_info_tokens`
is gone. The `OperatorNode` point stays with ITL-1019.
