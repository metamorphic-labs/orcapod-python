## `src/orcapod/databases/` — PipelineJob run time quadratic in rows

### DS1 — A job into a local `DeltaTableDatabase` spends most of its time on store bookkeeping
**Status:** resolved
**Severity:** medium
**Issue:** ITL-1173

Measured on `1531b8d5`, one function node `double(value)`, local disk, min of 3. A
10,000-row job took 16.25 s with the default `commit_every_rows=100`, against 1.13 s for
the pod without a job and 7.53 s for the job on `NoOpArrowDatabase`. At 100,000 rows it
took 346 s. Three costs grew with the rows stored:

- **Each commit rebuilt the table's dataset.** A commit loaded the table three times (the
  existence check, the writer's own reload when given a URI, the reload after the commit).
  `_extend_snapshot` also built `to_pyarrow_dataset` over every data file to find the one
  file the commit added. Per-commit cost rose from 8 ms to 37 ms over a 10k-row job. At
  100k rows commits took 192 of the 346 s, 131 s of it in the snapshot rebuild.
- **Each lookup walked every stored row.** Every lookup filters on the record id and on
  `__data_context`. The data-context position list holds every row, and
  `_row_index.matching_rows` intersected the position sets of all conditions. A lookup
  cost 100 µs at 10k rows and 250 µs at 100k (50 s).
- **A missing table was reopened on every lookup.** Until a table exists, every lookup
  tried to open it again, about 7 failed `DeltaTable()` opens per row. That cost 10.8 s
  of a 10k-row job committing once at node end, which is why one commit at node end
  (20.95 s) was slower than the default.

Also seen: deltalake logs one "Skipping column ... binary field" line per binary column
per write (1,000 lines at 10k rows). Changing that means setting a Delta table property,
which is a developer decision (F4, open).

**Fix:**
- `matching_rows` starts from the condition with the fewest rows and checks the others on
  those rows only.
- The database family remembers tables it found absent until its next flush;
  `table_exists` always checks again.
- An append commit is written through the table loaded for it. The snapshot is extended
  by reading only the commit's added files, found from the table's add actions and read
  with the format and filesystem of the dataset its rows came from. A partitioned table
  reads its dataset as before.

Stored rows, ids, hashes, paths, schemas and table properties are unchanged, and so is
the default commit interval (developer decision: it stays 100). The table is still loaded
afresh before each commit (developer decision): a handle refreshed in place could commit a
version gap into a store directory that was deleted and recreated.

Measured with the fixes, min of 3 at 10k rows against `main` in the same session:
- default interval: 12.96 s, against 15.81 s;
- `commit_every_rows=1000`: 11.02 s, against 12.33 s;
- one commit at node end: 10.58 s, against 20.95 s before.

At 100k rows (one run each): 159 s at the default interval (346 s before) and 117 s at
1000 (154 s before). Commits now cost 1.7 s of a 10k run (4.3 s before). The job's own
per-row work (7.5 s on `NoOpArrowDatabase`) is the largest remaining cost.

The deltalake "binary field" log line is explained in `docs/troubleshooting.md`, with the
`RUST_LOG` filter that hides it. No table property was set; that decision (F4) is open.

Follow-ups: ITL-1182 (`InMemoryArrowDatabase` lookups over the pending batch), ITL-1183
(peak memory at 100k rows), ITL-1184 (compaction: the append cost of deltalake itself
still grows with the file count), ITL-1177 / ITL-1179 (per-row hashing cost).
