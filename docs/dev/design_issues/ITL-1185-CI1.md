## `.github/workflows/run-tests.yml` — the SpiralDB integration job (ITL-1185)

### CI1 — `spiral-integration` failed on every push to `main`: SpiralDB rejected its sign-in
**Status:** resolved
**Severity:** high
**Issue:** ITL-1185

The `spiral-integration` job signed in to SpiralDB through a workload platform identity:
`SPIRAL_WORKLOAD_ID` plus a GitHub OIDC token (`id-token: write`). pyspiral 0.16.33 sends
that token to the API host as an OAuth token exchange, and the server stopped accepting
it (`422`: `grant_type` `token-exchange` unknown). Every test failed before any Orcapod code
ran, so every `Run Tests` run on `main` was marked failed even when the unit tests passed. The
repository variable `SPIRAL_PROJECT_ID` also named a project that no longer existed, and the
job ran only after the full test suite (`needs: test`), so each attempt to diagnose the
failure took about 40 minutes. SpiralDB has also retired workload client secrets, so a client
id and secret are not a replacement.

**Fix:** The job signs in with a workload private key, SpiralDB's current method: secrets
`SPIRAL_CLIENT_ID` (the workload id) and `SPIRAL_PRIVATE_KEY` (the private key as a JWK
naming its `kid`). pyspiral signs a JWT client assertion and requests a token from
`https://auth.spiraldb.com/oauth/token` with the `client_credentials` grant. The job requests no
OIDC token and no longer reads `SPIRAL_WORKLOAD_ID`. Its first step names each missing
setting, and refuses a key that is not a private JWK, printing names only. The two secrets are
given only to the two steps that read them, through the environment. The job runs beside the
test jobs, not after them. `RELEASING.md` ("SpiralDB integration job") covers the setup and key
rotation. A run by hand on the fix branch passed: 12 passed.
