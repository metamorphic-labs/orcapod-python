## `src/orcapod/core/operators/static_output_pod.py` — async barrier input

### AB1 — The async barrier path rebuilds its input with data-tags first and in the default data context
**Status:** open
**Severity:** medium
**Issue:** ITL-1205

An operator without its own `async_execute` collects its input rows and rebuilds them as a
stream (`StaticOutputOperatorPod._materialize_input_stream`, through `_rows_to_table`), then
applies its sync rule. Two properties of that rebuild make the async result differ from the
sync one, for every operator on this path.

1. Data order: `_rows_to_table` takes a data-tag (a tag that is also a data column, today a
   referential tag) from the tags and lays it out with them, so it leads the data columns.
   On the sync path a data-tag stays where the input table has it. For an input with data
   `a, x, y` and `x` a data-tag, `PolarsFilter` (and `TagBy`) give data `a, x, y` on the sync
   path and `x, a, y` on the async path.
2. Data context: the rebuilt input has neither the rows' data context nor a context column,
   so it takes the default context. Only one data context is registered today, so this is
   not observable yet.

The fix must keep the row-built layout of stored tables (`_in_row_order`) unchanged.
