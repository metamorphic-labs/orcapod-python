## `src/orcapod/core/nodes/function_node.py`

### FN3 — Reading a function node's stored results carried every column through Polars
**Status:** resolved
**Severity:** critical
**Issue:** ITL-1295 (related: ITL-1284, ITL-1249)

`FunctionJobNode._fetch_joined_records` joined the stored pipeline table and result
table as `pl.DataFrame` and converted the result back to Arrow. Every column went
through Polars, which changes or refuses some Arrow types: a `date64` tag off midnight
came back at midnight (also in a list or a struct), and a `decimal256` tag made Polars
panic, which no caller can catch. The stored tables were exact and a node's first run
showed exact values; every read of stored results did not: `node.as_source()`, a run of
a new job over the same database (results reused), `run(load_only=True)` and a saved and
loaded job. Downstream, a join of a reused node with a fresh source on the same tags found
nothing; a node added over a reused node stored the changed tag; and because a pipeline
entry id includes the tag values, every reuse run recorded new entries for the same
inputs under the changed tag (a downstream node's table grew from 2 to 4 rows). With a
`decimal256` tag, the reuse run itself crashed.

**Fix:** Polars only decides which stored rows belong together. It sees the bookkeeping
columns it filters and joins on (node content hash, ephemeral flag, record id, base
entry id, recomputation index) and a row number per table (`_row_frame`); every column
of the joined records is taken from the stored Arrow tables by those row numbers
(`_joined_from_stored`), in the layout Polars gave (a result column the pipeline table
also names takes `_right`), and the rows of a cross-session ephemeral miss are read from
the pipeline table. For every type Polars held exactly the result is what it was:
columns, order, names, types, nullability, rows (`docs/dev/scripts/itl_1295/dump_reads.py`
compares two checkouts). No hash, entry id, stored path or column moves. Tests:
`tests/test_pipeline/test_function_node_stored_values.py`.

**Fix (part 2):** the sort every presentation uses (`arrow_utils.sort_by_tag_columns`:
`as_table(columns={"sort_by_tags": True})`, `head().sort_by_tags()`, the notebook preview) fell back to
sorting the whole table with Polars when Arrow could not sort it (a list tag, or a struct
holding one), with the same losses. Now Polars orders only the prepared tag columns and row
numbers (`arrow_keys.polars_key_frame`, `arrow_keys.sort_key`) and the rows are taken from
the table. Nulls go last at every depth: a null list element or struct field after the
values beside it, as `GroupBy` orders a list and as Arrow orders a struct (so a struct tag
orders the same with or without a list tag beside it); before, Polars put them first. That
is the only order that moves (`docs/dev/scripts/itl_1295/compare_sort_fallback.py`
compares main's order with the new one). A tag type with no rule (a map, an interval, a
union, a list view) raises `TypeError` naming the column instead of a Polars error. Tests:
`tests/test_core/streams/test_sort_by_tags_values.py`. Not fixed here: the notebook
preview renders its rows through Polars, which panics on a `decimal256` column whatever
the sort (strict expected failures in that file).
