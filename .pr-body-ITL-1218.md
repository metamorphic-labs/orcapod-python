## What this adds

`SpiralDBTableSource.where(mapping=None, /, **columns)` returns a new source on the same table that reads only the rows in which every named column equals its value.

```python
events = SpiralDBTableSource("my-project-123456", "spike_event")
one_unit = events.where(unit_id=106)            # or events.where({"unit_id": 106})
one_session = one_unit.where(session_index=2)   # conditions add up
assert one_unit.content_hash() == events.content_hash()
```

### A restriction, not an operator

An operator (`SemiJoin`, `PolarsFilter`) is a node of the pipeline graph and part of its identity: a pipeline with a filter computes something else, with other hashes and other stored tables. A **restriction** is attached to the source. It chooses which rows flow and changes nothing else:

- the restricted source has the same `content_hash`, `pipeline_hash`, `source_id`, schema and system-tag column names as the unrestricted source;
- every row it reads is the unrestricted source's row, every column equal, record id included (SpiralDB record ids are the canonical JSON of the key, never a position);
- it adds no node. A job bound to a restricted source is the same job, run over fewer rows: results computed under the restriction are stored under the same identities and reused by a full run. Nothing stored is deleted; a job node shows its current run's rows and `node.as_source()` everything stored.

No golden hash, stored path or layout moves.

### One mechanism

`where()` and the existing `where=` constructor argument are one mechanism. The conditions live in one private frozen value, `_Restriction` (conditions plus the constructor's `limit`), which the scan, `head()` and the preview, `to_config` and the run summary all read; SpiralDB applies it in the scan. `where()` is two private steps: `_copy()` (a new object sharing no mutable state, no metadata re-read, so the pinned table version carries over) and `_apply_restriction()` on the copy, in place (validates, merges, refuses conflicts, moves the modified time).

### Recorded

- `RunSummary.restrictions`: `{slot: {"source_id": ..., "where": {...}, "limit": n}}` (`where` and `limit` only when set), for `job.run()`, `run_async()` and a node's `run()`; shown in the summary's text and HTML.
- The saved job already wrote `where` and `limit` in the source config and the loaded job already restored them; this PR tests it end to end.
- `bind()` does not compare restrictions: a restricted source fits the slot of the unrestricted one.
- `RestrictedAggregationWarning`: one per job run when a restricted source feeds a `GroupBy`, `Batch` or `MergeJoin`, naming the slot and the step (allowed: an aggregated row lists its members).

## Choices made

1. **Type-strict values, also for the constructor argument.** A value must be exactly of its column's Python type (no `bool` for an int column, no `int` for a float column, no NumPy scalar, no date string) and fit the column's Arrow type (range, timestamp precision, time zone awareness); `None` is refused (a null equals nothing). This is stricter than `where=` was: no existing test, documentation sample or call site had to change. Alternative: let SpiralDB decide, as before.
2. **`limit` applies to matching rows.** `SpiralDBTableSource(..., limit=10).where(x=1)` reads the first 10 rows that match, as the constructor did with both arguments. Alternative: "the matches among the first 10", which the scan cannot push down.
3. **The run summary is keyed by slot**, the name `bind()` takes, with the source id inside the value: a restriction belongs to the bound source object, so two slots on one table with different conditions are both reported.

## Intended later shape (not built here)

`source.where(r)` is `source.copy().apply_restriction(r)`; `_copy`, `_apply_restriction` and `_Restriction` are named so that making them public is a rename.

## Deliberately not built (rest of ITL-1218, and ITL-1219)

- `where()` on other source kinds and on `RootSource`; a `limit()` method (the `limit=` argument stays as it is);
- restrictions on streams and nodes; pushdown through operators;
- range, set and time-window predicates;
- a restriction shown in the pipeline diagram.
