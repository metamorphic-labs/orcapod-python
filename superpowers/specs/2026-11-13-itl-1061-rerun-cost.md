# ITL-1061: why re-running an unchanged pipeline is not instantaneous

Investigation only; no library change. Code references are to `main` at `89160c47`, which
includes PR #355 (ITL-1042/1052) and #352 (ITL-1043). Counts were taken on `97263e5b`, on PR
#355's head `963310fb`, and again on `89160c47`. The job-path counts are identical on all three
builds. The scripts and their raw output are in `superpowers/specs/itl-1061/` (see
[Reproducing](#reproducing)).

## Summary

**The developer's model** (ITL-1061): every node or stream keeps a timestamped in-memory cache
of its results. A newer upstream timestamp invalidates the cache, and the node recomputes or
reloads from the store. So after the first run, a re-run of an unchanged pipeline costs almost
nothing.

**Is it implemented?**

| Way of running | Implemented? | Where it stops holding |
|---|---|---|
| (a) Lazy streams read twice (`as_table`, `iter_data`, `head`) | **Yes on `main` since PR #355** (merged today). Every re-read costs 0. On `97263e5b`, `iter_data()` after `as_table()` re-ran the last pod (2,000 calls) because a chained pod stream was falsely stale. | Holds. Rebuilding the same steps as new stream objects recomputes everything, which is expected: new objects hold no cache. |
| (b) `PipelineJob.run()` twice on the same job, sync and async | **No.** Run #2 repeats everything except the function calls and the store writes. | The orchestrators never ask a node whether it is current: a **bypass**, not a bust. |
| (c) A new `PipelineJob` on the same store | **No.** It costs the same as (b) run #2, plus 4 store reads. | Same bypass. In-memory caches belong to node objects, so a new job has none to reuse; only the store can serve it. |
| (d) `Pipeline.run()` | `Pipeline` has no `run()` since PR #138 (ENG-456, 2026-05-20). The developer's "pipeline.run" is `PipelineJob.run()` today, which is row (b). | — |

**What run #2 of an unchanged job does** (sync, same job object, workshop-shaped pipeline of
2,000 + 6,000 rows; full tables in [A](#a-per-path-counts)):
- all 9 nodes execute again;
- 5 operator computations;
- 25,543 rows materialized into Python lists;
- 17,543 `Tag` and 17,543 `Data` objects built;
- 13 table rebuilds from rows;
- 4,000 function-node entry ids and 8,000 Arrow hashes;
- 0 function calls and 0 store writes.

With `SpiralDBTableSource`, add per run: 2 new scans, 8,000 record ids, 8,000 per-row key
hashes, and 8,000 more `Tag` and `Data` objects.

**Bypasses** (a cache exists and is not consulted):
1. **B1** `SyncPipelineOrchestrator.run` (`pipeline/sync_orchestrator.py:86-122`) and
   `AsyncPipelineOrchestrator` (`async_orchestrator.py:247-296`) start each run with empty
   buffers and call `execute()` / `async_execute()` on every node. Nothing under
   `src/orcapod/pipeline` reads `is_stale` or `last_modified`. After run #1 every node reports
   `is_stale == False` and holds a full result (`out/node_state.txt`). The information to skip
   is there; nobody asks.
2. **B2** `OperatorJobNode.execute` (`core/nodes/operator_node.py:1282-1341`) never reads its
   own `_cached_output_stream`. It checks only the store, in REPLAY mode (`:1310`), then always
   runs `self._operator.process(*input_streams)` (`:1317`). Only `run()` (`:1390-1406`) checks
   `is_stale` and the in-memory stream, and the orchestrators never call `run()`.
3. **B3** `FunctionJobNode.execute` (`core/nodes/function_node.py:1839-1980`) does keep its
   results (`_cached_output_datas`, 2,000 entries after run #1). But it can reach them only
   through the per-row key `compute_base_entry_id(tag, data)` (`:1892-1896`). That needs every
   input row as a `Tag`/`Data` pair with its data hash, so everything upstream must run first.
4. **B4** `SourceNodeBase.execute` (`core/nodes/source_node.py:366-389`) lists
   `iter_data()` again (`:386`).
   - `ArrowTableSource` and the sources that wrap it serve that read from their stream's
     `_cached_elements`: 0 new objects.
   - `SpiralDBTableSource` keeps nothing between reads: a new scan, a key hash and a record id
     per row, and new `Tag`/`Data` objects every run (`spiraldb_table_source.py:484`,
     `stream_builder.py:334`).
5. **B5** Between nodes, the sync orchestrator rebuilds an Arrow table from the previous
   node's list of rows (`_materialize_as_stream` → `_rows_to_table`,
   `sync_orchestrator.py:226`): 8 rebuilds per run. The new `ArrowTableStream` has no element
   cache, so the next node builds every `Tag`/`Data` again. Each operator node also rebuilds a
   table from its own output rows to keep it (`operator_node.py:1324`): 5 more rebuilds. The
   async path does the same at its barriers.

**Busts** (a timestamp moved although the content did not):
1. **T1** Every re-run stamps every operator and function node with a new `last_modified`
   (`operator_node.py:1330`, `function_node.py:1979`; async `operator_node.py:1755`,
   `function_node.py:3559`), even though the output is identical. Nothing reads these stamps on
   the job path today, so the bust costs nothing yet. It will once anything does: a skipping
   orchestrator would itself have to avoid restamping, and any stream that reads a job node
   lazily sees it change after every no-op run.
2. No other bust on the job path. `SpiralDBTableSource` and every `RootSource` keep their
   construction time (`core/base.py:300-326`), so a source never presents a newer timestamp.
   The lazy-path bust (a chained pod stream stamped before its input finished, ITL-1052) is
   fixed on `main` by PR #355.

**Missing invalidation** (the opposite of a bust; this blocks the simple fix):
- **M1** `SourceJobNode.last_modified` is the node's own construction time. It does not follow
  its bound source.
- `job.bind(sources={"experiments": <changed rows>})` leaves every downstream node
  `is_stale == False` (`out/node_state.txt`), so a skip based on `is_stale` alone would serve
  the old results. Today's run notices the change only because it recomputes everything.

**History in three lines.** The sync `Pipeline.run()` followed the model on `dev` from
2026-03-02 to 2026-03-14: `for node in topo order: node.run()`, and `OperatorNode.run` skipped a
non-stale node that held a cached stream. PR #85 (PLT-921, 2026-03-14) and PR #86 (PLT-922)
replaced that with orchestrators calling `execute()` for per-row observer hooks, with reuse
meant to come from the store alone. No tagged release ever had the skip, and the async path
never did. Details are in [C](#c-history).

**Recommended fix** (detail in [D](#d-making-a-second-run-instantaneous)):
1. One staleness gate, in `execute()`: return the node's kept result when the node is current
   and its result is complete.
2. The orchestrators pass upstream results as the upstream node's kept stream instead of
   rebuilding rows into a table.
3. `SourceJobNode.last_modified` follows its bound source, and binding stamps the node.
4. Skipping does not restamp a node.

On the measured pipeline, run #2 then does 0 computations, 0 per-row objects and 0 table
rebuilds. A new job object (c) still needs the store and is a separate, larger change.

This note sets no elapsed-time target: ITL-1055 leaves that number to the developer. What the
target should be measured on: the workshop pipeline (92k-row Spiral tables, notebook section
4) on the build the workshop uses, on an unloaded machine, as run #2 of the same job object
(today about 109 s against 123 s for run #1, at load about 18). The counter goals above are
the acceptance criteria this investigation can state. Section E's figures come from the small
fixture under `cProfile` and are not that baseline.

Timing: the developer has decided that the job-path fix lands **after the v0.3.0 tag**
(coordinator, 2026-11-13). Nothing here is needed for the workshop. The lazy path is already
fixed on `main` (PR #355).

## Method

- **Pipeline** (`rerun_counts.py`), shaped like the workshop's:
  - `sessions`: `ArrowTableSource`, 2,000 rows, tags `subject_id` and `session`.
  - `experiments`: 6,000 rows, a few `total` values null.
  - Steps: `experiments.drop_nulls(["correct", "total"])` → `group_by(["subject_id", "session"])`
    → `map_tags({"experiment_index": "experiment_indices"})` → `sessions.join(...)` →
    `accuracy.pod(...)` (Orcapod inserts a `SelectDataColumns` node to drop `booth`) →
    `grade.pod(...)`.
  - That makes 9 job nodes. The store is `InMemoryArrowDatabase`; one mode also uses
    `DeltaTableDatabase`.
  - The `spiral-*` modes read the same tables through `SpiralDBTableSource` over the
    repository's disk-backed pyspiral fake, with batches of 1,024 rows (the fake's default
    is 2).
- **Counters** (`counters.py`) are monkeypatched in at start. Each count is attributed to the
  node whose `execute` / `async_execute` is running, via a `ContextVar`. The metrics are listed
  in the module docstring.
- One process at a time, small inputs, no live Spiral, no test suites. One timing figure
  (`profile_runs.py`) was taken under `cProfile` at load average 3.1–3.3 on 10 cores.

## D. Making a second run instantaneous

### What must hold

- Same rows, hashes, record ids and stored tables as a full re-run.
- A changed source is always noticed.
- The rows a skip must **not** cover:
  - rows whose function failed (`_cached_output_datas` has no entry for them, so they must be
    retried);
  - a store attached or replaced after the run, which must receive its writes;
  - writes still pending from a failed commit;
  - a side-effecting node (`SideEffectJobNode`, or a pod with `ctx_arg`), whose delivery rules
    in `contexts/stored.account_for_stale_tables` run at the start of every run (`_begin_run`).

### Where the check belongs

**Option 1: in `execute()` (recommended).** At the top of each job node's `execute` /
`async_execute`, return the kept result, without reading the input, when all of these hold:
1. the node holds a **complete** result from a finished run: a new flag set at the end of a
   run with no failed rows, cleared by `clear_cache`;
2. `not self.is_stale`, with M1 fixed;
3. its store binding is the one that result was written under;
4. it is not side-effecting.

- Each node decides for itself, as in the March `run()`.
- Both orchestrators get it at once, with one constraint on the async one (below): a node may
  skip only when every upstream node of this run also skipped.
- Observers still see `on_node_start` / `on_node_end`; the per-row hooks would report nothing,
  or report "cached" per row without the per-row work. That needs deciding, because PR #85
  introduced the orchestrator precisely for per-row hooks.

**Option 2: in the orchestrator only.** Skip a node when it is current, and hand its kept
stream downstream.
- Simpler to read, but it duplicates node knowledge (completeness, side effects, store
  binding) in two orchestrators.
- It still needs `execute()` to accept "no input" for a skipped upstream.

**Option 3: both.** The node decides (Option 1). The orchestrator stops rebuilding tables from
row lists (B5): it passes the upstream node itself, or its `_cached_output_stream`, as the input
stream, instead of `_materialize_as_stream(list_of_rows)`.
- Without this, a node that does have work (because one upstream changed) still pays for
  rebuilding every unchanged upstream's rows.
- **Recommended: Option 1 plus the B5 part of Option 3.**

### What each node kind must keep

- **Operator node.** Keep `_cached_output_stream` (already kept) and its computed rows. Return
  `list(self._cached_output_stream.iter_data())`; the stream's `_cached_elements` makes that
  free on the second call. Better still, return the stream itself (B5).
- **Function node.** Keep `_cached_output_datas` in input order (already kept), plus the
  completeness flag. Return the kept pairs without computing entry ids.
- **Source node.**
  - Fix M1: `last_modified` = the max of the node's own time and the bound source's
    `last_modified`, and `bind` stamps the node.
  - Keep the materialized list (or rely on the source's own element cache), so that a Spiral
    source is not scanned again while its object is unchanged.
- **Restamping (T1).** A skipped node must not stamp itself. Otherwise every downstream reader
  of a job node sees a change after each no-op run.

### What "modified" means per source

- **`ArrowTableSource`, `DictSource`, `ListSource`, `DataFrameSource`, `CSVSource`,
  `DeltaTableSource`, SQLite / PostgreSQL table sources.**
  - All read their data at construction into an `ArrowTableStream`, so the content is fixed
    per object and its construction time is a correct `last_modified`.
  - A changed file or table is noticed only through a new source object (rebind or a new job).
    That is today's behaviour for these sources as well.
- **`SpiralDBTableSource`.**
  - Pins one table version per object (`asof`, or the table's version taken at construction,
    `spiraldb_table_source.py:299-304`), so its rows are immutable for that object, and the
    construction time is correct.
  - It must keep its rows (B4) to make the second read free. The memory is that of one
    materialized table, which a job already holds in `_cached_output_stream` downstream.
- **`PollingSource`.**
  - Moves `last_modified` from its cursor (`polling_source.py:867-872`): already a correct
    signal.
  - The node must not keep a "complete" flag across new data, which the timestamp provides.
- **`DerivedSource`** over a job node.
  - Construction time today. It does not follow the origin node's re-runs. Once the origin
    stops restamping (T1), it should report the origin's `last_modified`.
- **`CachedSource`.** Already compares its inner source's time (`cached_source.py:376-394`).

### Risks

- **Correctness under source change.**
  - M1 must land first, or together with the skip.
  - A source mutated in place (a user editing the `pa.Table` behind an `ArrowTableSource`) is
    not noticed. Orcapod forbids mutating inputs, so this is the user's error and is as
    undetected as it is today on the lazy path.
- **Memory.** A job already keeps every node's full output after a run (operator
  `_cached_output_stream`, function `_cached_output_datas`, orchestrator buffers while it
  runs). The fix keeps the same objects longer, with no new copies; option B5 removes copies.
  Keeping a Spiral source's rows adds one table per source.
- **Async.**
  - The async orchestrator starts every node's task at once over bounded channels (64 items,
    `pipeline/async_orchestrator.py:196-211`). A node that decides to skip at its start may
    do so before an upstream node, which does run, has restamped itself. The skipped node then
    never reads its input. That upstream blocks in `send` (`channels.py:144-147`) once its
    channel is full, and the run never ends. Closing the skipped node's own output does not
    release it (`_ChannelWriter.close`, `channels.py:149-163`).
  - So the async skip decision must be made **before the tasks start**, by the orchestrator,
    in topological order: a node skips only if it is current and every upstream node skips
    too. A node that skips does not read its input channels, and its upstream nodes' tasks are
    never started. Otherwise every input edge of a skipped node must be drained. This is an
    argument for Option 3, where the orchestrator holds the per-run decision and the node
    holds the "complete and current" test.
  - A skipped node must still send its kept rows and close its output channel.
  - A skipped function node must not start its executor.
  - Equivalence tests between sync and async (`test_async_sync_equivalence.py`) must cover a
    skipped run.
- **Observers and `RunSummary`.** A skipped node reports its rows as read from cache.
  `RunSummary` counts must stay meaningful. `PipelineJob.run` (`job.py` `_finish_run`) reads
  per-node counts from the run observer.
- **A new job object or process (c)** cannot use in-memory caches. Making it cheap needs a
  per-node memo key stored with the results: the input's identity plus the source versions and
  `where`/`limit`. That is the run-level memo the issue's Goals describe, and it is separate
  from this fix.

## E. Cost inside a first run

The ITL-1055 claim was that per-row `Tag`/`Data` construction and per-row record ids
dominate. The counters and the one profile (`out/profile_runs.txt`, Spiral fake, sync,
8,000 source rows, load 3.1) **confirm it in part**:

| item (run #1, under `cProfile`; total 25.5 s) | calls | cumulative s | removed on a re-run by the model? |
|---|---:|---:|---|
| function nodes' per-row store work (`_process_data_internal`: about 2 reads and 2 writes per row; 8,002 reads, 8,098 writes in all) | 4,000 | 12.0 | already absent on run #2 |
| `Tag`/`Data` construction | 25,543 + 29,543 | 4.4 + 2.6 | yes |
| function-node entry ids (`compute_base_entry_id`) | 4,000 | 3.6 | yes |
| `_rows_to_table` (orchestrator + operator nodes) | 13 | 2.2 | yes |
| Spiral per-row key hash (`_key_tokens`) + record id | 8,000 | 1.4 | yes, if the source keeps its rows |
| `hstack_tables` (inside `Tag.as_table` / `Data.as_table` per row) | 192,510 | 1.4 | yes |

- **Run #2 under the same profile:** 13.2 s, about half of run #1. All of it is the "yes" rows:
  - `Tag`/`Data` construction, 5.3 s;
  - entry ids, 3.5 s;
  - row-to-table rebuilds, 2.2 s;
  - Spiral key hashes, 1.4 s.
- **On the workshop pipeline** (92k-row Spiral tables, ITL-1055) the per-row key hash is the
  largest single item (45 s). There the function nodes see far fewer rows than the sources, so
  run #2 is close to run #1 (109 s against 123 s).
- **Correction to ITL-1055:** with a store, the first run's largest per-row cost on this
  pipeline is the function nodes' per-row store bookkeeping. It is not datagram construction.
- **What the model removes on a re-run:** everything in the "yes" rows. What remains inside a
  first run (vectorized record ids and key tokens, per-row store writes, building datagrams
  only where a function needs them) is ITL-1055 / ITL-1056 work.

## Out-of-scope findings (not fixed, not filed)

- **O1. Async calls functions more than sync for duplicate inputs.** On the same first run, the
  async function nodes call the function 94 + 64 times against 30 + 19 for sync. They write
  8,316 store rows against 8,098 (`out/job-async*.txt`). The likely cause, from reading and
  not traced: rows with equal input hashes are computed concurrently before the first result
  is stored, so the result memo does not deduplicate them. Stored results are still correct: equal inputs give equal outputs. The
  cost is extra function calls and writes, which matters for expensive or side-effecting
  functions.
- **O2. `FunctionPodStream.as_table()` returns `_cached_output_table` without the staleness
  check that `iter_data()` makes** (`core/function_pod.py:1338`). By reading only, not
  measured: over a `PollingSource` with new rows, `as_table()` would return the old table while
  `iter_data()` recomputes.
- **O3. The pyspiral fake hands out 2-row batches by default**
  (`tests/test_databases/fake_pyspiral.py:86`). Per-batch costs in tests over the fake are
  therefore about 4,000 times what they are on SpiralDB.

## Reproducing

All from the repository root, one process at a time:

```
uv run python superpowers/specs/itl-1061/rerun_counts.py lazy            # (a)
uv run python superpowers/specs/itl-1061/rerun_counts.py job-sync        # (b) + (c)
uv run python superpowers/specs/itl-1061/rerun_counts.py job-async
uv run python superpowers/specs/itl-1061/rerun_counts.py spiral-sync     # pyspiral fake
uv run python superpowers/specs/itl-1061/rerun_counts.py spiral-async
uv run python superpowers/specs/itl-1061/rerun_counts.py delta <dir>     # run twice: new process
uv run python superpowers/specs/itl-1061/node_state.py                   # B, M1, T1
uv run python superpowers/specs/itl-1061/profile_runs.py                 # E (one timing)
uv run python superpowers/specs/itl-1061/spiral_hash_callers.py          # who hashes in a Spiral read
```

To run against another build, put that build's `src` first on `PYTHONPATH`, for example
`PYTHONPATH=<worktree>/src uv run python …`. That is how `out/*-pr355-963310fb.txt` was taken.
