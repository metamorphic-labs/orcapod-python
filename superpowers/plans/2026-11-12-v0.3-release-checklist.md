## 3. Hash and type probe (against `v0.2.0`)

Tool: the golden suite, `tests/test_hashing/golden` (`cases.py`, `data/*.json`,
`test_golden_hashes.py`, `generate_golden_hashes.py`), plus `test_hash_label_rule.py`,
`test_type_annotation_golden.py` and `test_cross_process_stability.py`. No dedicated
v0.2-to-v0.3 script exists; none is added (developer decision).

Measured by key, golden files at `v0.2.0` against `main` (2026-11-12):

| File | Keys at v0.2.0 | Shared keys | Identical value | New keys on main |
|---|---|---|---|---|
| `arrow.json` | 53 | 53 | 0 | 63 |
| `semantic.json` | 54 | 54 | 0 | 31 |
| `datagram.json` | 171 | 91 | 0 | 188 |
| `pipeline.json` | 238 | 116 | 1 (an empty tag list) | 314 |
| `schema.json` | 92 | 74 | 17 (Arrow type strings, `bool`, `uuid`, `list[path]`, source id strings) | 77 |

What it shows: every stored hash moves, by design (data context `std:v1:default`, ITL-944,
ITL-910, ITL-942, ITL-945, ITL-953); the Arrow type strings that did not change are listed.
What it cannot show: that a given move is intended (all move), or anything about keys that
exist only on one side. The type column is the real no-unintended-change signal; a type
that moved is checked against its fragment. Rerun after the last hash-affecting PR.
